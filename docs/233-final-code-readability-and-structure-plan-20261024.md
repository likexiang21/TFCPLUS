## 一、执行时机

在现有已排定开发、缺陷修复、兼容处理及其验收/交付工作完成之后，新增一个独立收尾阶段，覆盖A、B及相关维护脚本、构建配置和开发文档。用户明确延期的验收仍保留待办状态；不得因暂时跳过测试，就将其记为完成并提前展开全面改名。若用户后续调整顺序，以最新要求为准。

## 二、命名要求

1. 变量、字段、方法和参数采用明确的业务名称，减少无意义缩写、临时名称和难以理解的单字母名称；短循环索引等局部惯用写法按语境保留。
2. Java类、接口及对应文件统一PascalCase，方法/字段/局部变量采用lowerCamelCase，常量采用UPPER_SNAKE_CASE，包名采用小写。遵循Minecraft、NeoForge、TFC公开回调和重写接口的既有签名。
3. 按职责审查My、Example、临时批次等泛化前缀是否仍有意义，逐项确定替代名称，不盲目批量替换所有同名字符串。
4. 脚本、工具、配置和新开发文档使用统一、简洁、有含义的文件命名约定，兼顾Windows/PCL路径长度。先列命名对照表，再迁移引用。
5. 名称表达现有真实行为，不借改名恢复废弃需求或改写已验收玩法。

## 三、结构和代码习惯

1. 先梳理职责和依赖，按注册、领域功能、方块/物品、容器、配方、客户端、JEI、数据/资源及维护工具等实际职责组织。保留A→B的既定依赖方向，A不反向依赖B。
2. 控制类和方法的职责，分解难读的长流程，明确输入、输出、拒绝条件和状态提交顺序；仅在存在真实复用时提取公共逻辑，避免堆叠空泛框架。
3. 统一缩进、括号、空行、import、访问修饰符、常量与错误处理习惯。删除确属无效的导入和死代码前，核查反射、注册、编解码器、生成工具及历史兼容入口。
4. 注释解释约束、原因、边界和必要兼容，不重复代码表面含义；修订过期注释，保留仍有效的来源与许可说明。
5. 区分活动源码/资源、生成草稿、构建产物、参考材料、历史交接和备份，明确每类文件的权威来源及再生成方法；没有确认用途的文件不得直接删除。

## 四、兼容和引用迁移

源码名称、类文件名称和文件系统路径可以在核对影响后整理；注册ID、资源标识符、配方ID、序列化字段/NBT键及模组ID不是普通变量，不为统一风格直接重命名。确有必要变更时，必须单独设计迁移/兼容方案，并保持旧存档可读。

每批迁移同步更新包声明、导入、资源路径、语言键、标签/配方引用、注册与客户端清单、JEI、手册链接、反射字符串、编解码器、构建配置、启动/打包脚本、生成模板和检查工具中的有效引用。特别核对Windows大小写不敏感但JAR内部路径大小写敏感的差异。

备份和历史交接保留原貌，通过新旧路径对照与当前入口索引帮助定位；不批量改写历史证据，也不把参考/备份副本误认为活动源码。不得移动或删除正式存档、用户PCL实例或受保护快照。

独立实现和禁止照抄要求持续有效，TFC Woodworking例外保持原授权范围。
