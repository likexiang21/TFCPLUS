# 下一阶段开发规划

**制定日期：** 2026-10-13  
**适用范围：** A（TFCFarmingPlus）与 B（TFCAgriculturePlus）  
**当前状态：** B 独立木工已经完成静态构建和门禁检查，等待最终 Minecraft 画面级验收；本文件记录从这一节点开始的工作顺序。

## 一、当前节点和执行原则

当前 B 木工已经具备 34 种木材的独立注册、去皮、去韧皮、劈木、锯木、木料堆、工作台配方、JEI、创造页和 Patchouli 入口。五项静态门禁、205/205 覆盖台账、1941 个资源 JSON 和离线构建均已通过，最新部署 JAR 的 SHA-256 为 `4059A95B0A0C66BC49754E4D434721D6FE77B25A9C505471DB627164D46B4C91`。

接下来按“实机验收 → B 新内容 → A/B 回归 → 再进入长期系统”的顺序推进。没有画面级证据的内容只记为“待验收”，不提前记为完成。

开发期间持续遵守以下要求：

1. 除用户明确授权的 TFC Woodworking MIT 迁移范围外，不直接照抄示例模组代码；新的业务逻辑使用项目自己的命名空间、状态机和配方实现。
2. 案板、石臼、干燥架、刀架、木料堆、未来的蚕架以及所有能放置或存储物品的方块，都必须先核对当前 TFC JAR 的公开接口，使用 `InventoryBlockEntity` / `TickableInventoryBlockEntity`、公开 item handler、容器菜单和同步机制。
3. 新增物品、配方和交互的 ID 必须来自当前依赖中已确认的注册结果；不能凭印象猜测 ID，也不能覆盖 TFC 或 Firmalife 的原有 ID。
4. 每个阶段结束都更新交接记录、构建结果、部署 JAR 校验值和未完成的实机项目。

## 二、阶段 C0：B 木工最终实机验收（下一步，P0）

这一步由用户在 Minecraft 中进行画面和鼠标操作验证，我负责根据结果修正代码。验收对象是 `docs/172-phase-b-woodworking-completion-20261013.md` 中的完整清单：

- 创造页、JEI 和 Patchouli 是否显示 B 自有内容，且不出现重复入口。
- 分别使用 TFC/AFC 的 `wood` 与 `log` 两种原始木材测试“去皮 → 去韧皮 → 劈半 → 劈四分”。
- 用锯测试支撑木、木板建筑部件、楼梯、台阶和栅栏等输出；确认原木不能跳过前置工序直接得到成品。
- 测试同树种堆叠、不同树种拒绝、潜行连续放入、纵向续堆、空手取出、破坏掉落、保存重载、自动化插入和燃烧转木炭。
- 在不安装 TFC Woodworking 的环境中检查 B 是否独立运行；若同时安装，检查 JEI 和实际交互是否仍只有一套入口。

调试命令 `/tfcagricultureplus_verify` 只用于快速定位流程，不替代画面观察。封窑仍按既定约定由用户自行实机测试，不把自动调试结果当成封窑的最终验收。

**阶段出口：** 用户反馈逐项记录；若发现问题，先建立缺陷条目并修复，再重新构建和部署。若全部通过，进入 C1。

## 三、阶段 C1：B 养蚕与蚕茧基础链（P0）

养蚕属于 B 模组。实现范围采用已经确认的极简设计，不加入育种、遗传、病害或复杂蜂群系统：

```text
Firmalife fruit_leaf / A 已有桑树叶
    → 养蚕架：空 → 养蚕中 → 已结茧
    → 蚕茧
```

施工顺序如下：

1. 先从当前 TFC、Firmalife 和 A 的 JAR/注册表确认饲料、桑树叶和后续丝相关的真实 ID，并写入 B 的 canonical ID 台账。
2. 新增 B 自有养蚕架方块、方块实体和必要的蚕茧/中间物品。养蚕架只做一方块和最小数量的物品，不重复注册 TFC 已有丝线或丝布。
3. 养蚕架采用 TFC 容器接口：服务器端唯一库存、公开 item handler、保存/加载、客户端同步、破坏/爆炸/替换掉落、满背包和自动化路径都要一致；渲染只读取容器和阶段状态。
4. 以“放入饲料开始计时 → 到期进入结茧状态 → 取出蚕茧”为核心状态机。拒绝错误输入时不消耗物品，完成后不能重复领取；具体时长在实现前写入配置或常量说明。
5. 为养蚕架、饲料和蚕茧补齐工作台/世界交互所需的配方、JEI、创造页、Patchouli 中英文说明和语言文件。
6. 增加独立的静态门禁，覆盖状态转换、配方引用、容器接口和资源完整性；再准备用户实机清单，不宣称已经通过画面验收。

**阶段出口：** 静态门禁和离线构建通过，B JAR 部署并记录校验值；养蚕架等待用户实机验证后才能进入后续丝加工。

## 四、阶段 C2：B 木工与设备回归收口（P1）

在 C0 反馈和 C1 静态实现之后，统一做一次 B 回归，防止新增内容破坏已验证功能：

- 复核木工 34 种树种、两种原始入口和可选 TFC Woodworking 兼容逻辑。
- 复核干燥架“最多八个相同物品、耗时与一个相同”的规则，并确认不同物品不能混入。
- 复核案板、石臼、刀架和木料堆的插入、取出、满背包、重载、破坏掉落和自动化访问。
- 复核 B 工作台配方、JEI、创造页和 Patchouli 与实际注册结果一致。
- 对每个发现的问题保留修复前备份、修复后门禁输出和实机复现步骤。

**阶段出口：** B 的静态门禁全绿，用户实机清单中已有结果的项目更新为“通过/失败/待复测”，不以日志替代画面证据。

## 五、阶段 C3：A/B 全局一致性回归（P1）

B 收口后，对整个项目做一次跨模组审计：

- 草莓只屏蔽自然生成，保持旧注册和旧存档兼容；创造页、JEI、Patchouli 不显示草莓入口。
- 可可种植和收获继续使用 `cupuacu`（大花可可树），发酵输入使用 Firmalife 原版 ID，不能新增平行可可豆体系。
- 汤、调味、案板、石臼、干燥架和已经确认正常的可可流程做回归，检查配方、标签、语言和手册是否仍能找到真实对象。
- 检查所有跨命名空间资源、覆盖台账、JSON 引用、重复注册、无效方块状态和 `replace: true` 邻居标签风险。
- 运行 A/B 构建、资源解析、覆盖台账、配方和容器契约门禁，部署前核对 build/libs 与 mods 中 JAR 的 SHA-256 一致。

**阶段出口：** 形成一份新的全局回归交接记录，明确哪些内容已有用户实机确认，哪些仍需要下一轮手动测试。

## 六、阶段 D：养蚕后的长期开发顺序

只有 C0～C3 收口后才进入长期内容，避免同时扩大未验收范围。建议顺序为：

1. **养蚕后处理：** 蚕茧煮制、抽出生丝、丝线和 TFC loom/silk cloth 的数据接入；优先复用 TFC 的 pot、loom 和已有丝绸定义。
2. **B 的加工链补齐：** 麦芽/麦芽汁/啤酒、果酱、面食、豆制品和香料等，优先使用 TFC/Firmalife 已有 barrel、pot、quern、heating 等设备，不为已有设备重复造方块。
3. **A 的收获物出口：** 按 146 物种台账逐项检查“种植 → 收获 → 至少一个加工或食用出口”，先补断链，再扩展新物种。
4. **温室、灌溉、地窖和自动化：** 先完成数据和容器契约，再设计自动化；每个能存物的设备都沿用 TFC 容器接口。
5. **C/D、动力系统和大规模自动化：** 保持暂缓，直到 A/B 的 P0/P1 没有未关闭的阻断缺陷。

## 七、每阶段统一完成标准

一个阶段只有同时满足以下条件才可以标记为完成：

1. 功能代码和资源已经写入项目，且没有违反独立实现、ID 和容器接口要求。
2. 对应静态门禁、资源解析和离线构建通过；部署 JAR 与构建产物校验一致。
3. 有清晰的实机验收清单；用户未验证的内容标为“待实机”，不写成“已完成”。
4. 交接文件记录变更、测试证据、已知限制、下一步入口和必要的回滚位置。

本文件作为 2026-10-13 之后的开发入口。用户已明确要求先推进 C1 养蚕基础链，因此 C1 已在木工实机验收尚未统一完成时启动；C1 不改变既有木工交互。C0 木工验收和 C1 养蚕验收都完成后，再进入后续回归和丝加工。
