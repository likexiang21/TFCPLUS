# AR2-A：水果原料、整派配方与食品信息修复交接

日期：2026-10-23。

## 一、结果和复杂度

本批已经完成源码/资源修复、静态核对、A/B离线编译打包及工作区/PCL_TFC部署，未启动游戏，未运行测试任务。实机合成、JEI显示、放置、分餐、重载及保质期观察仍待用户验收。

开始预估为高（4/5）。施工中发现整派不仅标签失效，还缺少腐烂拒绝和食品信息传递；仅修标签会开放一条把旧食品变成新鲜切片的路径，因此在窗口说明后扩大为整派这一条完整链，实际复杂度很高（5/5）。没有扩大到其他厨具或其他可放置食品。

## 二、原始证据

1. B的whole_pie配方使用c:foods/fruits。当前安装依赖和项目资源没有该复数标签定义；TFC与Firmalife使用c:foods/fruit。原来的F输入无法从这些声明得到候选。
2. A的gen-tags草稿仍把旧tfcfarmingplus:food/strawberry加入公共水果标签，和现行活动源不一致。原版tfc:food/strawberry已经由TFC正确归类，不需要把旧项目草莓重新公开。
3. 原整派是普通原版有序合成，没有拒绝腐烂原料，也没有输出食品信息修饰器。whole_pie物品本身没有食品定义，无法承载TFC日期。
4. 原PlaceableFoodBlock没有保存放入物品的信息。实体仅保存servings，分餐和拆除都直接new ItemStack生成切片，不能保留原料/整派的食品历史。

这些是当前源码和已部署旧JAR可见的路径，不是本轮已经复现的游戏现象。初始缺口及修复前备份检查保存在本批备份中。

## 三、修改后的整派流程

### 1. 输入、数量与配方编号

原配方编号crafting/whole_pie和FSF、空格D空格的图案保留：两份水果、一份甜味剂、一份面团，得到一份整派。原来八次分餐的数量保留。

F改用c:foods/fruit，S继续用tfc:foods/sweeteners，D继续用c:foods/dough。三个输入均通过TFC的and加not_rotten条件拒绝腐烂食材。没有新增面团或复制一套甜味剂，也没有改变现有公共面团标签的成员范围。

序列化类型改为正式依赖提供的tfc:advanced_shaped_crafting，结果使用stack和tfc:copy_oldest_food修饰器。该修饰器在TFC内读取整张合成输入，按其原生规则计算输出食品日期；本项目不自行复制或重写计算公式。

### 2. 整派食品信息

新增B自己命名空间内的tfc/food/whole_pie.json，ingredient指向实际tfcagricultureplus:whole_pie物品，edible=false，decay_modifier=0.75，与现有派切片一致。整派不可作为手持食品直接吃，仍通过放置后分餐使用。原派切片的营养、饱食和腐烂数据保持原值。

### 3. 放置与实体记录

仅当方块是WHOLE_PIE时，放置预检查拒绝腐烂物品；服务端放置完成后复制实际物品的食品记录。不会在方块实体构造器里修改库存、生成食品日期或触发同步，保留此前避免空level崩溃的修复。

实体仍继承TFC的InventoryBlockEntity，原有容器、份数和servings保存字段保留。新增私有pieFood快照和pie_food保存字段，承载日期/食品组件；这是食品信息，不是额外的一份可取物品。它不放进向漏斗开放的库存，不会被自动化抽走，也不会作为第二份整派掉落。

### 4. 分餐、拆除与腐烂

分餐切片和拆除剩余份数时，均通过公开FoodCapability.updateFoodFromPrevious接口继承整派记录。每次只产生既有的切片数量；最后一份分餐后方块移除，之后的拆除回调没有剩余份数可再次结算。

腐烂整派不能继续分餐。玩家仍可拆除，剩余切片按整派食品状态生成，不能借拆除重新变新鲜。没有增加每刻轮询；日期判断在原生食品组件和实际交互时发生。

其他整蛋糕、奶油蛋糕、巧克力蛋糕、奶酪、黄油、糖和果冻继续走既有分支。本批没有把它们改成新的整派日期规则，也不能把它们的日期传递说成已经修复。

## 四、旧世界兼容

所有方块、物品、实体和配方编号保留，份数不迁移到blockstate。保存仍调用TFC容器父类，新增pie_food通过Minecraft公开ItemStack编解码接口读写，读入时验证快照属于整派。

旧世界已放置的整派原来没有日期记录，无法从旧servings倒推出制作时间。首次加载时只对缺失食品记录且仍有剩余份数的整派初始化一次当前日期，并标记保存；之后不会因重载或逐份取用重置日期。这个兼容处理是开始记录，不是恢复了未知历史。已经保存的新记录按原值读取。

玩家旧库存中的整派接入食品定义后的实际表现，以及旧放置整派的一次性初始化，都列入实机清单。

## 五、旧草莓和生成器收口

A的gen-tags.ps1从浆果列表中移除旧项目strawberry。没有删除旧注册、旧模型或存档物品，没有恢复草莓灌木生成或显示。原版草莓仍由TFC原生水果标签提供。

生成器仅在moddev/.probe/generator-output/ar2a-tags-20261023运行，未向活动资源写入任何生成结果。草稿水果成员现在和活动源的27项相同：10种浆果、3种切片、14种已审核温带果实。三种切片的草稿排列顺序与活动源不同，但标签集合相同；活动文件本身未改，原顺序保留。

检查器按标签集合、无重复和replace=false判断，不把不影响标签语义的排列差异当作故障。没有为了消除一个旧条目而发布整份历史生成器草稿。

## 六、原料可达性矩阵与检查边界

新增B工具tools/verify-fruit-processing.ps1，并接入B的build-local.ps1构建前检查。输出在moddev/inventory/fruit-processing-20261023/fruit-processing.csv及同名JSON。

它读取48个外部依赖JAR的物品标签声明，以及A/B当前源资源；旧部署A/B JAR不参与来源合并，避免旧包反向污染源检查。共检查14份配方中的27处食品标签引用，涉及11种标签。结果列出原料候选、来源、缺失引用和静态状态，所有RuntimeVerified为false。

本批解析出水果52个声明候选、面团14个、甜味剂4个。水果候选含原版草莓，不含退休项目草莓。甜味剂为原版糖、Firmalife生蜂蜜和AFC两种树糖；面团范围沿用现有公共标签，没有在本批另加或删除成员。

候选非空只证明这些数据声明存在，不证明所有候选都已经在当前存档实测可获得，更不证明14份配方的全部腐烂、产量和加工行为都经过验收。仅整派食品信息路径属于本次Java修复范围。最终存档数据包顺序、KubeJS执行、JEI加载和玩家操作仍未验证。

检查器保守处理replace/条件/移除与重新加入冲突，不猜最终数据包优先级。初版因尚未处理原生jam标签中的remove，把该引用列为需审查；核实TFC在本文件剔除花生且其他当前来源未重新加入后，补齐局部移除解析，未修改果酱数据。当前果酱标签有25个声明候选。检测到跨来源重新加入时仍会报告需审查，不能用当前零问题结果推断未来任意数据包都会一致。

对修复前备份运行新检查得到14条按契约展开的差异，当前为0；14不是14个独立崩溃。另保留了初版草稿对比因切片顺序而失败的过程说明，最终按语义集合通过。

## 九、用户实机清单

先复制存档并核对实际启动实例的A/B JAR哈希。新标签和食品规则以实际加载数据包为准，旧压缩包或另外导入的实例不会被本次工作区部署自动更新。

| 项目 | 操作 | 预期现象 |
|---|---|---|
| JEI配方 | 查看整派配方和三类输入轮换 | 显示两份水果、甜味剂和面团，原版草莓及已分类项目果实可以作为候选 |
| 实际合成 | 按FSF、下方中间D的图案放入新鲜原料，分别用原版草莓、项目梨或瓜切片制作 | 产出一份可放置整派，消耗数量与原图案一致 |
| 腐烂拒绝 | 分别替换其中一份水果、甜味剂或面团为实际已腐烂物品 | 配方不成立，不因尝试合成消耗其他原料 |
| 合成食品信息 | 使用明显放置过一段时间但未腐烂的食材制作整派，对比新鲜原料产物 | 按TFC规则继承食品信息，不无条件变成全新日期 |

| 拆除余量 | 吃取部分后破坏剩余整派 | 只掉对应剩余份数，日期不刷新，不额外掉整派物品 |
