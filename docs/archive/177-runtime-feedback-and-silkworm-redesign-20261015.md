# 实机反馈、木工阻断分析与养蚕重做方案

**日期：** 2026-10-15  
**状态：** 木工 P0 资源修复与门禁已完成并部署；养蚕 P1 重做和无 TFC Woodworking 实机复测待继续执行。  
**适用版本：** 当前工作区 B 模组构建与 `logs/latest.log` 对应实例。

## 一、用户本轮实机反馈

这是用户对当前版本的实机结论，不是静态门禁结果：

1. B 木工模组的配方没有在 JEI 中正常显示。
2. 移除 `tfcwoodwork` 后，B 自有木工系统完全无法正常使用。
3. 因木工基础链被阻断，其他实机功能暂时没有继续测试。
4. 用户同时提供了 `C:\Users\asus\Desktop\养蚕改进.txt`，要求把当前养蚕箱机制整体推倒重做。

## 二、木工故障的直接证据与结论

### 1. 日志证据

本次运行日志 `logs/latest.log` 明确记录了 B 木工资源在 `RecipeManager` 阶段解析失败，例如：

- `Not a JSON object: "tfcagricultureplus:wood_sawed"`
- `Not a JSON object: "minecraft:item.axe.strip"`
- `Not a json array: {"action":"shoot_as_block", ...}`
- `Not a json array: {"Name":"afc:wood/log/teak", ...}`
- `[JEI] Registered 1 in-world recipes`

B 资源目录当前有 408 条木工世界交互 JSON（TFC 240 条、AFC 168 条），但运行时只有 1 条世界交互配方成功进入 JEI；因此“JEI 不显示”首先是配方在加载前已经被丢弃，而不是 JEI 搜索或分类单独隐藏。

### 2. 根因

B 当前 `InWorldRecipe.CODEC` 的实际契约要求：

- `result_state` 必须是带 `Name` 的方块状态对象；
- `result_items` 必须是数组，数组元素必须包含 `item` 对象和 `action`；
- `sound` 必须是包含 `sound`、`volume`、`pitch` 的声音对象。

当前迁移脚本 `tools/migrate-tfcwoodwork.ps1` 对来源数据做了字段改名，却没有把来源的单个 `resultItems` 统一包装为数组，也没有对所有迁移分支做最终 B 编解码契约校验，导致 136 个资源至少存在一种结构错误。部分迁移的木工掉落表也使用了旧的单对象 `conditions`/`entries` 结构，日志中同样出现 `loot_table ... Not a json array`。

因此，TFC Woodworking 在实例中存在时，用户看到的可用木工内容主要来自原模组；移除它后，B 自有配方因解析失败而全部失效。这解释了两项实机现象。

### 3. 对现有门禁的修正

此前“JSON 语法可解析”和“可选兼容检查通过”不能证明游戏能加载配方。后续门禁必须增加实际协议形状检查，至少覆盖全部木工 `in_world` JSON 与木工掉落表，并把期望加载数量写入构建报告。构建通过前不得再部署只通过文本/语法检查的 JAR。

## 三、`养蚕改进.txt` 中确认采用的重做要求

以下条目来自用户提供的附件，是新的功能需求；它们不继承当前一格养蚕架的行为：

1. 新增不可堆叠“成虫”物品，自生成起约七个游戏日耗尽耐久，耐久为零后消失。
2. 养蚕箱改为可打开容器，共 17 格：8 格生物/蚕茧/成虫输入、8 格树叶饲料、1 格只读蚕种产出。输入组每格只能放 1 个；饲料组每格可放 1 组。
3. 室温 15～30 时，蚕种经过 2～4 游戏日原位变为蚕。
4. 蚕每天消耗一份饲料；有饲料累计一次成长，无饲料累计一次饥饿；累计 10 次成长结茧，累计 3 次饥饿死亡并移除。
5. 蚕茧取出后用陶锅和水煮沸得到熟蚕；熟蚕与纺锤合成丝线，并消耗纺锤一点耐久。
6. 蚕茧留在养蚕箱中 3～5 日后原位变为成虫。
7. 箱内有至少两只成虫时，每天第三部分随机产出 1～5 个蚕种；成虫越多越接近 5 个；第三部分无空间则不产。

## 四、养蚕重做中的实现约束与待冻结口径

### 已冻结的实现约束

- 养蚕箱继续使用 TFC 原版容器契约：`InventoryBlockEntity`/`TickableInventoryBlockEntity`、标准物品能力、菜单同步、破坏掉落和保存恢复必须走同一套接口。
- 保留旧 `silkworm_rack` 注册 ID，增加旧一格状态到新 17 格状态的安全读取/迁移，避免旧存档直接丢失物品。
- 所有槽位校验必须在服务端完成；客户端只负责菜单显示，不能通过鼠标或自动化插入绕过槽位规则。
- 饲料集合必须以当前实例实际注册的 Firmalife 果树叶、A 桑树叶及其落叶 ID/标签为准，不能凭示例模组路径猜测。
- 丝线、织布机和 Firmalife/TFC 原版物品 ID 在施工前重新从当前依赖 JAR 核对；不直接照抄示例模组代码。

### 需要在施工设计中明确处理的边界

1. **成虫在任意容器中的寿命：** Minecraft 不会为未加载的普通箱子逐格执行物品 tick。实现将保存出生游戏时间，并在玩家背包、掉落实体、养蚕箱以及任意容器打开/变更时结算过期；若必须让未打开的任意箱子在后台即时删除，需要额外的全世界容器扫描，代价和存档风险应先评估。
2. **温度来源：** 以 TFC 当前公开气候/温度 API 读取养蚕箱位置的室温，不使用方块硬编码；施工时记录具体 API 和边界值。
3. **陶锅、纺锤和熟蚕 ID：** 从当前 TFC/Firmalife JAR 核对真实注册名。现有“蚕茧直接煮成丝线”的配方必须删除或迁移为“蚕茧 → 熟蚕 → 熟蚕+纺锤 → 丝线”。
4. **每日结算：** 以 TFC 日历日为单位，并保存上次结算日，区块卸载/重载不得重复结算，也不得补算出超过实际经过天数的成长次数。
