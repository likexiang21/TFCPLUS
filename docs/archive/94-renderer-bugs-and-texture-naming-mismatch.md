## 一、离线渲染器 \`render-tfc.ps1\` 的三处 bug

### bug 1：逐像素 z-buffer 的深度测试**符号反了**

\`Project\` 里 \`zd = y*sin(pitch) + zr*cos(pitch)\`，即 **zd 越大越靠近相机**
（pitch=0 时 zd=z；pitch=90 时 zd=y）。所以深度测试应当保留更大的 pdepth。

旧代码：
\`\`\`csharp
double dz = pdepth - zbuf[zi];
if (dz > 1e-9) { continue; }                     // 更近的反而被拒！
if (dz > -1e-9 && faceIdx >= zbufFace[zi]) { continue; }
\`\`\`
⇒ 凡是比已写入像素**更近**的面全被丢弃 ⇒ **屏幕上只剩最先画的那一片**。
这就是「十字变成一片」的直接原因。\`drawn++\` 在面循环末尾**无条件自增**，
所以它照样报 \`faces=4/4\`，把这个问题完全掩盖了 —— 我此前一直拿这个数字当"画了四个面"的证据。

修正为：
\`\`\`csharp
if (dz < -1e-9) { continue; }                    // 明显更远 -> 被挡
if (dz <= 1e-9 && faceIdx >= zbufFace[zi]) { continue; }  // 共面 -> 面序号小者胜
\`\`\`

### bug 2：\`zbuf\` 初值方向反了

修好符号后**整幅变空白**：\`zbuf\` 初值是 \`double.MaxValue\`，而"更近"现在等于"更大"，
第一片面算出的 \`dz\` 是极大负数、被判成"更远"直接丢弃 ⇒ 一个像素都写不进去。
初值必须是 \`double.MinValue\`（最远）。

### bug 3：面光照（shade）计算写在写 \`data\` **之后**，从未生效

PowerShell 端先把 \`$ftint\` 写进 \`data\`，**之后**才计算 shade 并改写 \`$ftint\`
⇒ 写进去的永远是旧值。实测证据：渲染出的颜色恰好是贴图原色 \`RGB(45,125,45)\`，
而 north/south 本应是 0.8 倍。

同时补上 MC 的 \`shade\` 语义：element 上的 \`"shade": false\` = **不接收方向光**。
**原版 \`minecraft:block/crop\` 的四个 element 全是 \`shade:false\`** ⇒ 作物的面就是贴图原色，
不乘任何系数。

### 附带修正：\`up\`/\`down\` 的共面偏置方向

\`+bias\` = 更靠前（会胜出）。水平板从上方看到的是 \`up\` 面，必须让 \`up\` 胜；
旧代码让 \`down\` 胜，方向是反的。

## 二、更严重的问题：\`.probe\` 里的 \`minecraft:block/crop\` 模型是**伪造的**

### 伪造版（我们一直在用的那份）
\`\`\`json
[{"from":[0,0,8],"to":[16,16,8],"rotation":{"axis":"y","angle":-45,"origin":[8,8,8]}},
 {"from":[8,0,0],"to":[8,16,16],"rotation":{"axis":"y","angle":45,"origin":[8,8,8]}}]
\`\`\`
只有 **2 片** ±45° 旋转的板。

**这份模型在数学上必然自重合**：
- 沿 x 的板转 −45° ⇒ 方向 (cos45, sin45) = (0.707, 0.707)
- 沿 z 的板转 +45° ⇒ 方向 (sin45, cos45) = (0.707, 0.707)
⇒ 两片落到**同一条对角线**上（无论旋转符号取哪种约定都成立，因为 Δθ=90° 让初始垂直的
两片变成平行）。**所以用这份模型无论怎么修渲染器都画不出十字** —— 这也解释了为什么
我此前的"偏心竖条测试"在 yaw 0/30/45/60/90 下**永远只显示一条**。

### 真品（从 \`.minecraft/versions/<版本>/<版本>.jar\` 内
\`assets/minecraft/models/block/crop.json\` 原样导出，1263 字节）

**4 片互相平行的竖直板**，**没有任何 rotation**：

| # | from | to | 面 |
|---|---|---|---|
| 1 | \`[4,-1,0]\` | \`[4,15,16]\` | west(uv 正) + east(uv **反**) |
| 2 | \`[12,-1,0]\` | \`[12,15,16]\` | west(uv **反**) + east(uv 正) |
| 3 | \`[0,-1,4]\` | \`[16,15,4]\` | north(uv 正) + south(uv **反**) |
| 4 | \`[0,-1,12]\` | \`[16,15,12]\` | north(uv **反**) + south(uv 正) |

- \`ambientocclusion: false\`，四个 element 全部 \`"shade": false\`
- 两对平行板各错开 **4 格** ⇒ 这才是"十字"
- 高度是 **−1 … 15**（不是 0…16）⇒ 植株比方块底面低 1 格、比方块顶面低 1 格

**已修复**：真品已写入
\`.probe/ref-tfc/assets/minecraft/models/block/crop.json\` 与
\`.probe/lab-assets/minecraft/models/block/crop.json\` 两处。

### 修好后的自检（证据 \`.probe/texture-design/px/Z2-YAWS.png\`）
偏心竖条贴图在真品模型下 p20、yaw 0/30/45/60/90 五连渲染：
- yaw 0 / 90 报 \`faces=4/8\`（两片板侧对相机、投影退化成线，被 \`det≈0\` 正确跳过）
- yaw 30 / 45 / 60 报 \`faces=8/8\`
- 画面上是**多片分开的竖板 + 板间黑色空隙**，黄条出现在不同板上

⇒ **十字结构第一次被真正渲染出来。**

他看的是 14:37 批量生成的那套（无基部、颜色单一、像珊瑚枝），
**而我这几轮一直在改 \`X_N.png\`（死贴图），所以用户看不到任何改善。**

## 五、经验（本轮新增，全部有实测支撑）

45. **测一个渲染器之前，先确认它渲染的模型是真的。** 我花了大量轮次去"修"一个数学上必然自重合的
    假模型；期间用户的每一次质疑（"十字根本没被渲染出来"）都对，而我用 \`faces=4/4\` 这个
    **无论画没画上都自增的计数器**来自我安慰。
46. **计数器必须在"真的写了像素"时才自增。** \`drawn++\` 的位置让一个整幅错误的渲染报出了正常值。
47. **改贴图之前，先确认模型引用的是哪个文件名。** 用
    \`grep 模型 json 里的 textures 键\` 反查，不要靠猜命名规律（\`X_N\` 与 \`X_age_N\` 同时存在）。
48. **凡"逐文件产出"的脚本，收尾必须做一次"引用闭合审计"**：
    实际文件 ↔ 模型引用，双向差集都要为空。658 张死贴图就是缺了这一步的代价。
49. **批量脚本覆盖同名文件前必须备份**；\`X_age_N\` 被整体覆盖是 385 张手绘工作"消失"的直接原因。
