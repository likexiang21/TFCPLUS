## 三、所有要求的统一解释

### 3.1 开发优先级

顺序固定为：

1. 修复会导致重复物品、空标签、错误配方、存档损坏或构建误判的根因。
2. 修复设备、木工、封窑和食品链的实际状态机。
3. 补齐 A/B 已设计但未完成的系统级内容。
4. 最后恢复新的物种、食品类别、厨房家具、C/D 模组等长期开发。

### 3.2 代码来源

- 示例模组、反编译代码、教程业务代码不得直接复制。
- TFC、NeoForge、Firmalife 的公开 API 可以调用，但业务逻辑必须按照本项目输入、状态、输出、失败分支、保存和兼容需求独立设计。
- 用户唯一明确的代码例外是 TFC Woodworking 的木工代码和现有配方；例外只覆盖木工，必须保留来源/许可记录，并独立补齐 AFC 木材和项目兼容层。
- 发现旧代码可能直接搬运时，要先登记、核对来源，再独立重写；只改包名或注释不算重写。

### 3.3 三项已确认的内容决策

- **草莓：** 不注销 `tfc:plant/strawberry_bush`，只关闭新世界自然生成，并从创造模式物品栏、JEI 和 Patchouli 手册中隐藏；项目普通草莓和野生草莓保留种植/采收方块，果实统一掉落 `tfc:food/strawberry`，种子逻辑保持。
- **可可种植/采收：** 沿用此前制作的“大花可可树”实现，先从当前 A 源码核对其准确注册名和四件套，不凭中文名猜 ID；树体和采收表现不改成另一套平行实现。
- **可可加工：** 保留发酵流程；原料使用 `firmalife:food/cocoa_beans` 及其 `firmalife:dried` 状态，后续接回 Firmalife 的烘焙/可可粉/巧克力链。禁止重复注册另一套基础可可豆体系。

### 3.4 验收等级

- L1：能编译。
- L2：资源、注册表、标签、协议和覆盖台账通过。
- L3：日志能证明模组、配方和数据重载成功。
- L4：用户在实际世界中看到正确画面并按正常路径完成鼠标交互。

L3 不能代替 L4。封窑完整玩家测试继续由用户负责；CUA 没有原生窗口桥接时不能猜坐标或伪造交互通过。

## 四、全局缺陷清单

## P0：必须先解决的功能和数据根因

### P0-1 草莓存在三套来源，且原版灌木仍对玩家可见

**证据：** A `MyItems.STRAWBERRY`、A `MyCrops.STRAWBERRY_CROP`、A `MyWildCrops.WILD_STRAWBERRY` 与 TFC `tfc:food/strawberry` 并存；草莓掉落表和 Firmalife plantable 曾指向项目食品；B 还有 `DRIED_STRAWBERRY`。

**整改：**

- 删除项目自有草莓食品和草莓干的活跃注册、模型、食品数据、语言、配方和创造页引用。
- 普通作物和野生草莓掉落 `tfc:food/strawberry`，种子掉落不变。
- 只覆盖/移除 TFC 草莓自然生成入口，不注销其注册。
- 从创造模式物品栏中隐藏 `tfc:plant/strawberry_bush` 的物品入口；不能误删 `tfc:food/strawberry`，也不能隐藏项目普通作物、项目野生草莓或草莓种子。
- 从 JEI 隐藏原版草莓灌木的物品/方块入口，保留原版草莓果实及其真实加工配方。隐藏实现必须使用 JEI 公开 API 或项目已有兼容入口，不能修改 JEI 本体。
- 从 Patchouli 手册隐藏草莓灌木的条目、配方映射、物品映射和相关世界生成说明；保留项目草莓种植、收获和原版草莓用途的手册内容。
- 需要分别验收“注册仍在”“世界不自然生成”“三个玩家可见入口隐藏”，不能把隐藏入口误当成注销注册。
- 重新检查 TFC/ Firmalife 草莓果酱、plantable、标签和旧存档兼容。

### P0-2 调味配方引用了空/错误汤标签

**证据：** TFC 真实标签为 `c:foods/soup`，包含 `tfc:food/vegetables_soup`；当前 B 的 `seasonable_soups` 使用不存在的 `tfc:food/vegetable_soup`。当前配方同时把自定义标签当作输入和输出入口。

**整改：**

- 输入改为真实 `c:foods/soup`，所有标签必须经过展开检查且非空。
- 输出继续使用原汤 `copy_input + tfcagricultureplus:seasoned` trait，不注册“调味汤物品”。
- 明确腐烂输入、重复调味、食品数据和新鲜度处理。

### P0-3 可可加工重复注册，但种植/采收沿用项目大花可可树

**证据：** Firmalife 已有可可豆、烘焙豆、可可粉、可可脂和相关配方；A 当前也保留此前制作的“大花可可树”实现。问题是加工基础物品和配方重复，而不是要抹掉用户已经制作并指定继续使用的树体表现。

**整改：**

- 保留 A 当前“大花可可树”的种植、树体生长和采收表现；施工前从 `MyFruitTrees`/`MyBranchFruits` 和资源中确认准确注册 ID，避免把 cupuacu/cocoa 中文名混淆。
- 将该树的采收结果接到 `firmalife:food/cocoa_beans`，不再让它掉落项目自有基础可可豆。
- 删除 B 自有基础可可豆、烘焙豆、可可粉和巧克力平行入口；不得因为清理加工物品而删除大花可可树的种植/采收注册。
- B 只保留真正独有的发酵流程；发酵输入为 Firmalife 可可豆的 `firmalife:dried` 状态。
- 发酵后输出必须接回 Firmalife 烘焙豆、可可粉和巧克力链；项目不得再注册第二份基础可可豆。

### P0-4 干燥架的抽象层错误

**证据：** `DryingRackBlockEntity` 使用 B 自定义 `DryingRecipe`，固定读取 `recipe.duration()`，要求 `level.canSeeSky(pos.above())`，并按项目专用输出物品完成。Firmalife 的真实干燥行为使用 `DryingRecipe.getRecipe(ItemStack)`、`assemble`、`FLConfig.SERVER.dryingTicks` 和 `firmalife:dried` trait。

**整改：**

- 设备查询改为 Firmalife 公开 `DryingRecipe` API。
- 删除项目专用干草莓、干姜、干姜黄、干白菜丝、干可可豆等基础物品。
- 结果是原物品加 `firmalife:dried` trait；保留食品组件和新鲜度语义。
- 计时、雨天、保存、取出、腐烂拒绝和破坏掉落按 Firmalife 行为独立实现，不复制 Firmalife 业务源码。
- JEI 展示也要从旧自定义 recipe type 迁移到真实可用的 Firmalife/B 组合入口。

### P0-5 木工流程重复且产量错误

**证据：** B 当前有 239 条 `in_world` 规则；旧 `saw_planks_*` 会直接从去皮原木生成异常数量木板，且与 TFC Woodworking 的树皮、韧皮、半原木、四分之一原木、支撑木、木料和锯末链并行。

**整改：**

- TFC 木材交由 TFC Woodworking 的权威流程，删除 B 冲突配方。
- AFC 木材按同一输入/输出契约独立实现，不能静默映射到 TFC 木种。
- 每种木材建立物料守恒和工具耐久台账。
- 木料堆、燃料、掉落、模型和 blockstate 同步清理，不能留下“删除了配方但还注册着物品/方块”的半链。

### P0-6 封窑批次模型不完整

**证据：** `BurningTimberPileBlockEntity` 只沿竖直方向扫描最多 64 段；点火时每段单独转换，完成时以第一段为底逐段读取，任何一段未完成就直接返回；覆盖检查在单个 BE 上进行，无法稳定表示完整连通堆的批次。

**整改：**

- 先核对 TFC 原生 Pit Kiln 公开契约。
- 若能安全复用，优先接回 TFC 原生封窑/计时/产物行为。
- 否则独立设计有上限的连通批次：点火记录批次、密封条件、总单位、剩余时间和保存状态；完成时一次性结算；重载后恢复；破坏/缺盖/雨水等异常有明确结果。
- 产物使用 TFC 木炭 ID，不创建第二套木炭。
- 玩家点火、封存、等待和取炭仍由用户手动验收。

### P0-7 A 资源健康检查本身不能在当前 PowerShell 环境运行

**证据：** `moddev/tfcfarmingplus/tools/verify.ps1:63` 使用 `ConvertFrom-Json -AsHashtable`，Windows PowerShell 报“不存在该参数”；因此 `healthcheck.ps1` 当前不能证明 A 资源健康。

**整改：**

- 改为兼容 Windows PowerShell 5.1 和 PowerShell 7 的 JSON 读取方式，或在脚本入口明确锁定 `pwsh` 并检查版本。
- 脚本必须用原生解析器逐文件检查 JSON，不能因为检查器自身崩溃而误报“通过”。
- jar 一致性从大小/时间升级为 SHA-256，同时保留大小/时间用于快速提示。

### P0-8 文档、jar 和运行环境版本漂移

**证据：** 文档 00 的 TFC/Firmalife 版本与当前 `mods` 实际版本不同；历史交接中的 hash、配方数量和资源计数不能直接代表当前源文件。

**整改：**

- 每次阶段开始先生成环境 manifest：MC、NeoForge、Java、TFC、Firmalife、AFC、Woodworking、JEI 版本和 jar hash。
- 旧文档保留为历史记录，不再当作当前 API 依据。
- 所有 canonical ID、公开 API 和 JSON 字段以当前 jar 重新核对。

## P1：会造成系统性错误或后续维护失控的缺陷

### P1-1 源码来源和独立实现审计不完整

主类注释仍有“完全照抄 TFC 的形态”等表述；B 的世界内配方机制虽然曾记录为零 mixin 融合实现，但需要逐文件登记实际来源、接口调用和独立业务逻辑。

**处理：** 建立 source-provenance ledger。对疑似搬运代码做相似度/结构审查；需要保留的标准注册骨架与业务实现分开记录；不满足用户规则的存量业务代码进入独立重写批次。

### P1-2 A 植物真实种植闭环仍缺少 L4 证据

A 的作物、野生作物、果树、灌木和自建 BE 注册已经有大量静态检查，但完整真实路径仍需要逐类验证：放置、气候判定、生长计时、成熟、采收、种子返还、腐烂/枯死、重进世界和客户端渲染。

特别风险：

- `MyBlockEntities` 使用自建类型包住 TFC 类型，TFC 的静态 helper 曾被确认可能按类型查找而静默失效。
- `MyFruitTrees`、`MySeasonalPlantFix`、`MyGrowingFruitTreeBranchBlock` 的计时器和树干结果必须用实例 API 验证。
- `FastGrow`、调试命令和实机启动脚本的文档有过时表述，测试加速必须与正常生长验证严格分离。

### P1-3 B 设备的存档、同步、破坏和异常路径需要系统回归

案板和石臼已有用户“正常”的反馈，但不能因此跳过以下全局检查：

- 空手、持原料、持工具、腐烂输入、无配方输入、成品取出和满背包。
- 方块破坏、活塞/替换、爆炸、区块卸载、保存重载和多人客户端同步。
- 工具耐久、物品数量、食品组件和拒绝操作时的原子性。

当前 `MyBlocks.dropContentsOnBreak` 的注释已明确爆炸掉落留到后续批次；这属于存档和物品丢失风险，不能在最终交付中继续隐藏。

### P1-4 配方和 JEI 不是同一套事实来源

当前 B 同时存在自定义 recipe type、JEI category、JSON 目录和运行时查询。历史文档对 `in_world` JEI 分类、干燥配方数量和运行时注册的状态有过不同结论。

**处理：** 为每类配方生成“JSON → 注册 type → 方块交互 → JEI → 实机操作”的闭环表；运行时日志和实际 JEI 页面都要记录，不能只统计文件数量。

### P1-5 自定义命名空间与邻居覆盖需要按注册表而不是文件名审计

当前 B 覆盖台账 199/199 通过，只能说明文件路径一致，不能证明：

- 输入输出 ID 真实存在。
- 标签展开后非空。
- 同一行为没有两套配方。
- 删除资源后不存在孤儿引用。
- 邻居更新后仍保持语义兼容。

**处理：** 新增 canonical ID、tag expansion、recipe reachability、duplicate output、orphan reference 和 override diff 五项门禁。

### P1-6 旧存档风险没有按“注册保留/行为迁移/方块实体迁移”分层

简单删除项目物品、方块或方块实体会导致旧区块出现未知 ID、容器内容丢失或食品组件无法读取。草莓灌木已明确采用“保留注册、关闭自然生成”，可可/干燥/木工也必须分别制定兼容策略。

**处理：** 每个删除项标记为：

1. 可直接删除的未发布资源；
2. 必须保留旧注册 ID 的兼容对象；
3. 需要数据迁移或旧配方兼容的对象；
4. 不能在本批次安全处理、必须暂缓的对象。

### P1-7 共享脚本和生成器存在覆盖已认可资源的风险

历史文档记录过 `X_N`/`X_age_N` 命名错位、批量覆盖手绘贴图、PowerShell BOM/大小写哈希键、双段接缝和假 crop 模型等问题。

**处理：**

- 生成器只能有一个产出源，手改 JSON 必须回写设计/生成记录。
- 任何批量写入前建立逐文件备份和 dry-run 清单。
- 先反查模型引用文件名，再生成/修改贴图。
- 真实 TFC 模型、2D 放大图、3D 渲染图和接缝审计四者缺一不可。
- 保留 `.probe/lab-assets`、`.probe/lab-old`、`.probe/lab-new` 历史快照，不得清理。

### P1-8 视觉资源仍有历史未收口项

根据 `INBOX.md`、`93`、`99`、`116` 和 `120~125`，以下不能被“资源交叉引用通过”掩盖：

- 部分几何/模型只完成离线检查，未有真实游戏画面。
- 莲座、叶球、双段作物、果树叶子和若干成熟/枯死状态仍有历史弱项或未重新复核。
- 旧版/占位贴图、真实模型引用和用户已认可的手绘作品必须逐物种区分处理，不能全局替换。
- blockstate 覆盖全部属性、零厚度面轴、UV、越界、接缝和双段整株连贯性必须列入资源门禁。

本阶段不擅自重画用户未要求重画且已认可的贴图，只做审计和证据补齐。

### B 模组新增明确计划：养蚕与丝

用户已确认养蚕归入 B 模组，不再按旧主方案中 C 侧的历史排期解释。B 完成当前 P0/P1 缺陷整改后，加入以下极简链：

```text
Firmalife fruit_leaf / A 的桑树叶
  → 蚕架喂养（空 → 养蚕中 → 已结茧）
  → 蚕茧
  → TFC pot 煮茧缫丝
  → 丝线
  → TFC loom / TFC silk_cloth
```

设计边界：

- 养蚕是 B 的一方块、三到四个项目物品和三到四条配方/交互链。
- 只做“喂 → 生长 → 结茧 → 收”，不做育种、品种遗传、病害或复杂蜂群系统。
- 优先复用 `firmalife:fruit_leaf` 和 A 已有桑树资源，不修改邻居物品，不重复注册丝绸布。
- 蚕架是可放置物品的方块，必须遵守下一节的 TFC 容器接口规则。

### 所有可放置物品方块的统一接口要求

从下一批代码开始，石臼、干燥架、案板、刀架、蚕架以及以后任何能放入物品的方块，统一按 TFC 原版的容器接口和公开基类设计。具体实现前必须从当前 TFC jar 确认对应公开 API，优先使用 `InventoryBlockEntity` / `TickableInventoryBlockEntity`、TFC 的容器菜单/`ItemStackContainer`、公开的 item handler 和同步机制；不得再为每个方块单独维护无法互操作的 `content` 字段、手写保存协议或只在鼠标路径可用的临时库存。

统一要求包括：

1. 一个明确的槽位/容量定义，服务器端是唯一权威状态。
2. 通过 TFC/NeoForge 正式容器接口完成插入、取出、菜单同步、保存/加载和必要的自动化访问。
3. 拒绝输入必须原子化，不消耗原料和工具；完成输出不能重复领取或丢失。
4. 方块破坏、爆炸、替换、区块卸载、重进世界、多人客户端和满背包都要有一致行为。
5. 渲染层只读取容器状态，不自行保存第二份物品；JEI/手册显示与真实容器配方来源一致。
6. 施工记录中必须写清引用的 TFC 公共接口、独立实现的状态机、兼容字段和测试证据；不得直接复制 TFC 业务实现。

## 六、何时采用局部修复，何时推倒重构

默认先做分阶段、可回滚的局部重构，因为 A/B 已有旧注册和旧存档风险。以下任一条件满足时，才切换到 B 某个子系统的完整重构：

1. 同一机制存在两套无法通过兼容层统一的 recipe type/BE 状态机。
2. 旧状态字段无法映射到目标行为，继续修补会丢失物品或进度。
3. 静态检查通过但 L3/L4 连续失败，根因位于架构而不是单个 JSON。
4. 代码来源审计确认现有业务实现无法满足独立实现规则。
5. 修复一个功能会反复破坏另一个功能，且共享层没有稳定边界。

如果触发完整重构，必须先建立旧 ID/旧状态迁移表、备份、回滚方案和最小可运行版本；不能直接删除旧注册后再观察崩溃。
