# TFC 农业重制缺陷整改总方案

**制定日期：** 2026-10-09  
**文档状态：** 方案冻结，尚未开始本轮代码修复  
**适用范围：** `tfcfarmingplus`（A）、`tfcagricultureplus`（B）、开发工具、构建流程和交接记录  
**依据：** 工作区指令、开发规则、主设计方案、历次交接记录、已安装模组 jar 的实际内容，以及用户提供的《修改建议.txt》

**用户已确认的本轮决策：**

- 草莓灌木只禁止自然生成；保留注册 ID 和旧存档读取能力，不做危险的注册注销。
- 可可发酵流程保留，但所有可可原料和后续基础物品改用 Firmalife 的原版注册 ID，不再维护重复的可可豆体系。

> 本文是本轮整改的唯一施工方案。开始修改前必须先读本文和 `DEVELOPMENT_RULES.md`。本文中的“已确认”表示已经由源文件、资源文件、jar 或交接记录得到证据；“计划”表示尚未实施，不能写成已完成。

## 一、整改目标

暂停原来的新内容开发，先把用户实机发现的七组问题彻底收口：

1. 草莓只保留一套可用的果实来源，项目作物和野生草莓掉落 TFC 原版草莓；删除项目自有草莓果实和草莓干物品。
2. 调味配方引用真实的 TFC 汤类标签，调味结果仍然是原汤本身加上调味 trait，不创建空的或不存在的“调味汤物品”。
3. 可可树、可可豆及后续加工优先使用 Firmalife 已注册的原始内容，不再维护平行的重复可可树和可可豆。
4. 保留已经实机反馈正常的案板和石臼逻辑，整改期间不得无关重写；调味、草莓、可可修复后重新回归。
5. 修复封窑/木炭生产，使完整木料堆能够正确封存、计时、完成并产出木炭。封窑的完整玩家操作仍由用户手动验收，本方案不会擅自把它标为通过。
6. 依据 TFC Woodworking 的真实加工顺序重建木料流程，消除“原木直接锯出 16 块木板”等错误，并保证 TFC 木种与 AFC 木种不会同时存在两套互相冲突的加工规则。
7. 把干燥架改成与 Firmalife 原有干燥垫相同的行为：接受可干燥食品，输出原物品加 `firmalife:dried` trait；不再制作“干草莓、干姜黄、干白菜丝、干可可豆”等项目专用平行物品。

本轮完成标准不是“能编译”或“JEI 中能看到配方”，而是：资源引用正确、注册表闭合、配方输入有真实物品、输出符合目标行为、构建和部署可复现，并把尚未进行的实机项目如实留给用户验收。

## 二、已经确认的项目规则

### 2.1 规则优先级

后续出现冲突时按以下顺序执行：

1. 用户当前明确要求。
2. `AGENTS.md` 与 `DEVELOPMENT_RULES.md` 中的工作区硬约束。
3. 本文的整改目标和验收标准。
4. 近期实施文档和旧交接文档中的设计推导。
5. 外部模组的行为只能作为事实参考，不能代替用户口径。

### 2.2 禁止直接照抄示例模组代码

- 不得把示例模组源码、反编译结果或教程业务代码复制后仅改包名、类名、变量名或注释。
- 参考模组只能用于确认输入、输出、公开接口和时序；实现前必须先写本项目自己的状态、数据结构、异常处理和兼容方案。
- TFC、NeoForge、Firmalife 等正式依赖的公开 API 可以调用。
- 用户明确给出的例外仅针对 TFC Woodworking：允许使用其代码和现有配方作为木工整改的参考或迁移依据。该例外只覆盖木工流程，不能扩大到草莓、可可、调味料、干燥架或封窑；来源、许可、实际采用范围和本项目的改动必须记录。
- 如果发现存量代码可能直接来源于示例模组，先登记来源，再按本项目需求独立重写或明确保留理由；改注释不算重写。

### 2.3 工程与依赖方向

```text
A  (tfcfarmingplus)  ←  B (tfcagricultureplus)
C  独立，只依赖 TFC ← D 只依赖 C
```

A 不得依赖 B，B 的新增数据写入自己的命名空间。写入 TFC、Firmalife 或 AFC 的标签必须是追加式，禁止用 `replace: true` 覆盖邻居内容。

### 2.4 施工纪律

每个批次必须先列出文件、输入、输出、数据格式和完成条件，再修改。每个批次结束时必须区分“已实现、已构建、已检查、用户已验收”。开发过程中阶段变化必须在窗口说明“我目前正在执行哪一步”。

构建顺序固定为 A 后 B。构建成功后才允许部署到 `mods`。构建、部署、运行日志、jar 哈希和备份位置必须写入交接文档。不能用日志注册成功代替游戏画面和真实鼠标操作通过。

封窑的完整玩家测试继续交由用户负责；本项目不能因为自动检查通过就替用户勾选封窑。

### 2.5 资源、美术和工具规则同样继续有效

- 本轮主要处理注册、配方、方块实体和木工逻辑，不借整改名义批量重画贴图，也不删除 `.probe/lab-assets`、`.probe/lab-old`、`.probe/lab-new` 等历史快照。
- 如果整改触及模型或 blockstate，必须先确认模型实际引用的文件名；`X_age_N` 与 `X_N` 不能混用。零厚度元素的面方向必须和零厚度轴匹配，blockstate 必须覆盖方块的全部属性，模型修改后要做几何、UV、越界和接缝检查。
- 真实游戏画面仍是视觉验收标准。设计稿、像素统计、`faces` 数量或离线脚本结果不能代替进游戏观察。
- 结构型贴图继续按工作区既定的逐像素手绘规则处理，禁止用一个模板批量刷出同质化低质量贴图；若某项不需要重画，就保持现状。
- PowerShell 脚本必须保持 UTF-8 with BOM，脚本注释使用 ASCII；文本读写使用显式 UTF-8，修改后用解析器检查。路径必须规范化，数组表达式中的计算值先存变量，哈希键冲突使用区分大小写的比较。
- 修改脚本、资源生成器或共享工具前要先重读当前文件；同一批次把同类改动集中完成，不用脆弱的行号或短锚点重复插入。

### 2.6 来源与许可记录

本项目保留各参考模组的许可和来源说明：TFC/NeoForge/Firmalife/AFC/TFC Woodworking 的实际接口和数据以当前安装 jar 为准；ARR、GPL 或 CC BY-NC-SA 来源只能用于观察玩法和设计，不能带入业务代码、资源或文本。即使木工部分有用户明确例外，也要在实施记录中写清楚采用了哪些公开行为、哪些配方、哪些代码，以及本项目独立改动了什么。

## 四、七组问题的目标行为与改法

### 4.1 草莓：合并果实来源，保留种植闭环

#### 目标行为

- 游戏中新建世界不再生成项目自有的重复草莓果实和草莓干物品。
- 项目的普通草莓作物和野生草莓方块仍然可以存在、成长和采收。
- 两者的果实掉落统一为 `tfc:food/strawberry`。
- 种子返还、野生掉落概率、成熟状态和原有种植逻辑不改变，除非实际资源闭合检查要求同步调整。
- `tfcfarmingplus:food/strawberry` 和 `tfcagricultureplus` 的 `dried_strawberry` 不再被注册、掉落、配方或创造页引用。

#### 实施办法

1. 先建立草莓注册与引用表，确认 A 的自有果实、B 的干草莓、TFC 原版草莓、TFC 草莓灌木和 Firmalife plantable 的全部入口。
2. 将 A 的普通作物掉落表和野生作物掉落表改为 `tfc:food/strawberry`，只改变果实结果，不删除种子结果。
3. 删除 A 自有草莓食品的数据、模型、语言和贴图引用；删除 B 的 `DRIED_STRAWBERRY`、其食品数据、配方、模型、创造页和语言键。
4. 禁止新世界自然生成 `tfc:plant/strawberry_bush`。只修改或移除对应的 worldgen 入口，不注销方块注册，不删除旧区块仍可能引用的 ID；这样可以避免删除注册造成的存档和加载问题。
5. 本轮不再讨论彻底注销 `tfc:plant/strawberry_bush`。旧区块中的植株保持可读取，后续仅验证新世界和新生成区块不再自然出现该灌木。

#### 验收

新世界中只看到目标草莓植株；普通作物和野生草莓都掉落 TFC 草莓，种子逻辑保留；JEI、创造页、掉落表中不再出现项目草莓和草莓干；旧测试存档能够读取。

### 4.2 调味料：使用真实汤标签和 trait 输出

#### 目标行为

- 姜粉、姜黄粉、黑胡椒粉等所有 B 香料粉可以与 TFC 所有真实汤类组合。
- 配方输入使用 `c:foods/soup`，不依赖错误的单数或空标签。
- 成品不是一个新注册的“调味汤物品”，而是原汤物品复制食品数据后附加 `tfcagricultureplus:seasoned` trait。
- 调味后仍保留原汤的营养、新鲜度和食品组件；已经调味的汤不能重复加料。
- 腐烂汤和腐烂香料必须被拒绝且不消耗错误材料。

#### 实施办法

1. 删除或停用错误的 `seasonable_soups` 标签；配方直接引用 `c:foods/soup`。如果保留项目标签，只能由脚本验证其非空且逐项来自真实 TFC 注册物品。
2. 在加载期做标签非空检查，遇到空标签或未知物品直接使构建/校验失败。
3. 保留项目自有 `seasoned` trait，但确认它只表示调味状态，不冒充 TFC 的 `salted`、`brined` 或其他食品语义。
4. 使用 `tfc:copy_input` 和 `tfc:add_trait` 输出，避免创建新的汤类物品和第二份食品数据。
5. 增加静态配方检查：输入标签至少命中一项真实物品；结果 modifier 顺序正确；不存在 `vegetable_soup` 这类错误 ID；重复调味有明确拒绝条件。

#### 验收

JEI 能显示汤和香料的组合；至少用蔬菜汤、果汤、谷物汤各测一次；成品 tooltip 有调味标记，原营养与新鲜度保留；重复调味和腐烂输入均拒绝。

### 4.3 可可：完全采用 Firmalife 的树和豆

#### 目标行为

- 游戏中可可树、可可枝、可可叶和可可豆使用 Firmalife 的注册内容。
- A/B 不再注册第二套可可树、可可豆、烘焙可可豆、可可粉或巧克力基础物品。
- 所有项目加工配方以 `firmalife:food/cocoa_beans` 为入口，并尽量复用 Firmalife 已有的烘焙、可可脂和粉末配方。
- 允许保留“发酵可可豆”这一真正新增的中间状态，但它只能作为项目独有工艺中间物，不能重新注册一套平行可可豆链。

#### 实施办法

1. 先反查 Firmalife 的实际注册 ID、食品数据和已有配方，禁止凭旧文档或名称猜测。
2. 从 A 的 `MyItems`、`MyFruitTrees`、`MyBranchFruits`、`MyCrops` 和相关资源中移除项目自有 cocoa 注册及世界生成入口；保留必要的兼容读取策略，不在旧存档中硬注销未知方块。
3. 从 B 的 `MyItems`、食品数据、模型、语言和配方中移除重复的 cocoa beans、dried cocoa beans、roasted cocoa beans、cocoa powder、dark chocolate 等项目物品。
4. 将案板、干燥、密封桶、加热、石臼和合成等入口逐条改成 Firmalife 原始可可豆或 Firmalife 已有的后续物品。
5. 保留项目的可可发酵中间物和密封桶流程，但发酵原料必须使用 Firmalife 的原版可可豆及其真实干燥结果；发酵完成后重新接回 Firmalife 的烘焙、可可粉和巧克力链。发酵中间物是项目新增工艺状态，不得再注册第二套可可豆、烘焙豆或粉末基础物品。

#### 验收

JEI 和创造页只出现 Firmalife 的树、豆和后续基础物品；项目配方能从原版可可豆进入后续流程；不再出现两套同名可可豆。可可加工的输入、输出、食品数据和腐烂条件逐步记录。

### 4.4 案板和石臼：保留正常部分，做回归保护

案板、石臼已经有用户“测试正常”的反馈，本轮不进行结构性重写。整改只做三件事：

1. 检查删除草莓、可可、干燥配方时没有误删案板/石臼注册和公共接口。
2. 重新构建并做静态资源和配方回归，确认原有刀具耐久、敲击次数、腐烂拒绝和取出逻辑未被影响。
3. 在最终手动清单中保留一条短回归项，用户只需确认整改后仍能正常操作；不把旧的“正常”反馈扩展成对新调味、草莓、可可的通过证明。

### 4.5 封窑与木炭：先纠正批次模型，再决定是否接回 TFC 原生逻辑

#### 已知风险

当前 `BurningTimberPileBlockEntity` 以单个方块实体的 `units` 处理，点火后没有稳定保存完整连接堆的批次边界；`finish` 扫描范围和各段状态同步不足，容易出现只处理一段、覆盖条件不一致、保存重载后进度丢失或看起来无法产出木炭的情况。

#### 计划方案

1. 先以 TFC 的真实 Pit Kiln 行为和公开 API 为基准，确认当前自定义封窑是否有必要继续存在。
2. 如果 TFC 的公开接口能安全复用，优先将项目木堆接入 TFC 原生的封存/计时/产物契约，删除重复的炭化状态机。
3. 如果不能安全复用，则独立重写项目状态机：点火时识别完整连通堆并生成稳定 batch 标识；每段记录同一批次、密封时间、剩余时间和目标产物；保存/加载后恢复；完成时一次性结算所有有效段；任何未覆盖段不得被假报为已封窑。
4. 明确隔热、覆盖、雨水、批次上限、断电/退出重进和破坏方块的处理。扫描范围必须有上限，不能无限 BFS。
5. 产物使用 TFC 木炭或 TFC 木炭堆的真实注册 ID，不能再造第二套“木炭”。

#### 验收

自动检查只能证明状态字段、注册和配方闭合。完整的点火、封存、等待、取炭和重载过程仍列为用户手动验收；本方案不把这项提前标记为通过。

### 4.6 木料加工：以 TFC Woodworking 为行为基线重建

#### 目标工序

木料流程必须能被玩家按顺序理解，不能直接把原木锯成 16 块木板：

```text
原木 + 斧头
  → 去皮原木 + 树皮
去皮原木 + 斧头
  → 去皮芯材 + 韧皮
去皮芯材 + 斧头
  → 半原木
半原木 + 斧头
  → 四分之一原木
半原木 + 锯子
  → 支撑木 + 锯末
四分之一原木 + 锯子
  → 木料 + 锯末
```

具体产量、工具损耗、掉落物和方向状态以 TFC Woodworking 已有配方实际核对结果为准；任何自定义扩展必须记录物料守恒。

#### 实施办法

1. 对 TFC 的 20 种木材，移除 B 中与 TFC Woodworking 重复的 `axe_debark_*`、`saw_planks_*`、`timber_*` 入口，让一个明确的木工系统负责它们。
2. 只使用 TFC Woodworking 的公开行为和现有配方作为木工例外；保留许可与来源记录，不把其代码扩散到其他功能。
3. 对 AFC 独有木材，若 TFC Woodworking 没有覆盖，使用 B 自己的注册物品和独立实现补齐同一工序；不能把缺少的木材静默指向另一种木材。
4. 删除或停用会让“原木→木板”与“原木→去皮/芯材”同时可用的冲突配方。一个输入在相同工具和条件下只能有一个明确的主流程。
5. 检查 `TimberBlocks`、木料堆、燃烧堆、掉落表、模型和燃料数据是否仍引用已删除的项目木材部件；删除无引用资源，保留旧存档读取所需的注册兼容项。
6. 为每类木材生成独立的输入输出台账，验证没有 16 倍产量、循环配方、错误命名空间或空标签。

#### 验收

逐木种检查原木第一次使用斧头产生去皮原木和树皮；随后能继续得到芯材、半原木、四分之一原木、支撑木和木料；锯子不会直接大量生成木板；TFC 和 AFC 木材不互相串材。

### 4.7 干燥架：复现 Firmalife 干燥垫的公开行为

#### 目标行为

- 干燥架是一个一格输入、按时间完成、完成后取出的干燥设备。
- 它接受 Firmalife/TFC 真实的可干燥食品，不限于项目自造的四种食品。
- 输出使用 `copy_input` 加 `firmalife:dried` trait，保留原物品身份、数量和食品组件。
- 不注册 `dried_strawberry`、`dried_ginger`、`dried_turmeric`、`dried_cocoa_beans`、`dried_napa_cabbage` 等平行干燥物品。
- 雨天、进度保存、腐烂拒绝、完成提示、取出和破坏掉落与 Firmalife 干燥垫的公开行为一致；不额外加一个会把正常露天干燥判死的天空可见条件。

#### 实施办法

1. 读取 Firmalife `DryingRecipe.getRecipe`、`assemble`、`FLConfig.SERVER.dryingTicks` 和干燥垫的天气/计时契约；只调用公开 API，独立实现项目方块的交互。
2. 删除 B 自定义 `DryingRecipe` 类型和固定物品输出配方，改为查询 Firmalife 干燥配方并使用其组装结果。
3. 把自定义配方目录改成通用 tag/trait 语义：已有 Firmalife 配方直接复用；缺少的项目食品只补“输入标签 + `copy_input` + `firmalife:dried`”配方，不新增干燥版物品。
4. 让方块实体保存输入、进度和完成状态，服务器端只在有输入时计时；雨天按 Firmalife 规则处理；重载后恢复。
5. 删除创造页、模型、语言、掉落表和配方中所有项目专用干燥物品引用。

#### 验收

至少测试原版/TFC 水果、项目草莓、香料和蔬菜各一项；输出仍是原物品并出现 `firmalife:dried` tooltip；不存在项目专用“干某某”物品；雨天、保存恢复、完成取出和腐烂拒绝与干燥垫一致。

## 五、实际施工顺序

### 阶段 0：冻结与审计基线

- 暂停新作物、新设备、新食品和美术批量工作。
- 备份 A/B 源码、当前 jar、运行日志和现有交接文档。
- 从 TFC、Firmalife、AFC、TFC Woodworking jar 重新导出本轮涉及的注册 ID、标签、配方、掉落表和公开 API。
- 单独记录两项已确认决策：只关闭草莓灌木自然生成，不删除其注册；保留可可发酵，但所有发酵输入改用 Firmalife 原版 ID。
- 生成“保留 / 删除 / 改写 / 只兼容旧存档”的文件台账。

**门禁：** 没有完整台账和备份，不进入代码改动。

### 阶段 1：规范注册表和资源引用

- 先建立 canonical ID 清单：草莓、汤、香料、可可、干燥 trait、木工中间物、木炭。
- 给检查脚本增加未知 ID、空标签、重复输出、删除后残留引用和邻居标签替换检查。
- 先处理资源引用和注册闭合，避免代码修好但旧 JSON 仍把错误物品重新带回来。

**门禁：** 每个保留注册项至少有注册、模型/语言、需要时的食品数据、配方入口或掉落出口；每个删除项全局无活跃引用。

### 阶段 2：草莓与可可去重

- 先完成草莓掉落统一、自有食品删除，并关闭草莓灌木自然生成入口。
- 再完成可可树、豆和后续基础物品接回 Firmalife，同时保留并改正可可发酵流程的输入 ID。
- 这一阶段不改干燥架主逻辑，只删除会制造重复物品的旧干燥配方和注册。

**门禁：** 全局搜索不得出现应删除的项目草莓/草莓干/重复可可基础物品；新配方全部命中真实 canonical ID。

### 阶段 3：调味料修复

- 修正汤标签和 recipe 输入。
- 保留 `seasoned` trait 机制，删除空标签依赖。
- 添加静态和运行前配方自检。

**门禁：** 所有汤类标签非空且可展开，配方结果不产生第二个汤物品。

### 阶段 4：干燥架重构

- 先以 Firmalife 干燥垫为行为规格，独立重写 B 的查询、计时、状态保存和交互。
- 删除自定义固定输出和专用干燥物品。
- 完成静态检查后再构建，不把自定义旧 recipe type 与新 API 并存。

**门禁：** B 代码中不再依赖旧 `DryingRecipe` 结果物品；每个保留干燥配方都返回 `copy_input + firmalife:dried`。

### 阶段 5：木工重建

- TFC 木种先清理重复规则，再接入 TFC Woodworking 的真实链。
- AFC 木种按相同工序独立补齐。
- 最后处理木料堆、燃料和掉落，避免旧方块继续引用已删除部件。

**门禁：** 任一木种的同一输入不能同时命中旧“直接木板”和新分段流程；产量台账无 16 倍异常。

### 阶段 6：封窑修复

- 先完成 TFC 原生行为核对，再选“接入 TFC”或“独立批次状态机”。
- 实现保存恢复、连通堆、密封条件和完成结算。
- 只做静态、构建、日志和必要的自动化状态检查；完整玩家点火/取炭仍留给用户。

### 阶段 7：整合、构建和部署

1. A `clean build`。
2. A 资源交叉引用和注册台账检查。
3. B 使用最新 A jar 执行 `clean build`。
4. B 边界、许可、覆盖台账、注册和 JSON 检查。
5. 检查 `mods` 中只有本次构建的 A/B jar，没有旧 jar 与新 jar 并存。
6. 记录构建输出、jar 大小、SHA-256、备份目录和已知未验收项。

**门禁：** 任一阶段失败则停止部署，不用“先复制到 mods 再试”的方式掩盖构建问题。

### 阶段 8：用户手动验收与收尾

- 先启动当前客户端并确认进入测试世界，再按清单逐项测试草莓、调味、可可、干燥架、木工和旧存档。
- 案板和石臼做短回归。
- 封窑仍由用户自行完成。
- 如果 CUA 原生窗口桥接不可用，不猜坐标、不伪造通过结论，直接在清单中标记“阻塞/待用户”。
- 收尾时恢复 `options.txt` 等启动前设置，写入本轮交接文档。

## 六、构建前后必须执行的防错门禁

### 6.1 内容和注册门禁

- 所有配方输入和输出都必须能从实际 jar 或本项目注册表解析。
- 所有标签必须非空；项目标签中的每个成员都必须是已注册物品。
- 邻居命名空间标签全部是追加式，禁止 `replace: true`。
- 删除物品后全局扫描注册类、资源、配方、掉落、标签、创造页和语言文件，不能残留活引用。
- 禁止同一用途存在两个项目物品；允许保留的唯一新增中间物必须在台账中说明用途和去向。
- 食品配方必须记录腐烂条件、新鲜度/营养传递、数量和工具耐久影响。

### 6.2 结构和编码门禁

- 新 JSON 用原生解析器逐文件解析，不接受“看起来像 JSON”。
- blockstate 覆盖方块全部属性；资源引用必须指向存在的模型和贴图。
- 批量脚本使用显式 UTF-8，避免 BOM、乱码、换行丢失和 PowerShell 数组表达式错误。
- 修改模型后执行几何、面轴、UV、越界和接缝检查；本轮不因整改需要擅自改变已冻结的贴图审美规则。

### 6.3 构建与部署门禁

- 构建不能并行；先 A 后 B。
- 删除资源或注册项时使用 clean build，避免旧产物掩盖错误。
- 构建未成功前不复制到 `mods`。
- 部署前后记录 jar 哈希，清理旧版本重复 jar。
- 运行日志只作为 L3 证据；没有进入世界和实际画面/交互，就不能写 L4 通过。

每次整改批次至少按以下顺序运行现有门禁，并把输出保存到批次记录：

1. A 项目的资源交叉引用校验（`tfcfarmingplus/tools/verify.ps1`）。
2. B 项目的边界和协议校验（`tfcagricultureplus/tools/check-boundaries.ps1`）。
3. B 项目的覆盖台账校验（`OVERRIDE-REGISTRY.md` 对应的 `verify-coverage-ledger.ps1`）。
4. B 的注册检查；涉及循环注册或运行时展开时，使用新游戏日志的 `verify-registry.ps1 -FromLog`，不能把静态误报当作最终结论。
5. 项目健康检查（`tfcfarmingplus/tools/healthcheck.ps1`）和逐文件 JSON 解析。

删除资源、注册项或配方类型的批次必须使用 clean build；Gradle 构建不能并行，后台任务未确认完成前不能启动客户端。部署前还要对比 `build/libs` 与 `mods` 中的时间、大小和 SHA-256，确认没有旧 jar 与新 jar 并存。

### 6.4 回滚门禁

以下任一情况立即停止后续批次并从最近备份回滚：

- 进入世界出现注册表、数据包、未知 ID 或模型加载错误。
- 发现旧存档中的方块实体、食品组件或容器无法读取。
- canonical ID 被误删，或出现同名重复物品。
- 构建脚本与工作区实际路径不一致。
- 自动操作遇到 `Selected model is at capacity. Please try a different model.`，按用户要求停止自动客户端操作，不继续尝试。

## 九、当前结论

当前项目不适合继续堆叠新内容。最安全的路线是先清理重复注册和错误标签，再按 Firmalife/TFC 的真实公共行为重建干燥架、木工和封窑。这样可以先消除用户已经观察到的“两个物品并行、空 tag、错误干燥产物、木工产量异常”等根因，也能让后续构建在资源引用、注册表、配方和依赖方向上有明确的失败门槛。

本文件完成后仍未开始代码修复。下一次开始施工时，第一条窗口进度必须说明“我目前正在执行阶段 0：冻结与审计基线”，并在阶段 0 的备份、jar 盘点和文件台账完成前不修改功能代码。
