## 二、🔴 新发现：**剪影重复（同形）是系统性问题**（本轮新增审计）

### 2.1 方法

``.probe/texture-design/silhouette-audit.ps1``：把每张 16×16 PNG 的 **alpha 掩码**转成 256 位字符串，
按字符串分组 —— 同组 = **剪影逐像素完全相同**（判据 5「轮廓多样性」的硬违规）。

### 2.2 结果（实测）

| 项 | 数值 |
|---|---|
| 贴图总数 | 657 |
| 不同剪影（掩码）数 | **513** |
| **重复组** | **67** |
| 最大一组 | **15 个物种共用同一剪影**（age1） |

**完整 67 组清单**：`.probe/texture-design/px/silhouette-dup-report.txt`

### 2.3 分级（必须人工区分，不能一刀切）

| 级别 | 特征 | 例子 |
|---|---|---|
| 🛑 **废稿级**（同族不同物种共用剪影） | 一组里是**不同物种**的同一龄 | `[1] 15 个物种 age1`：arugula/celery/cotton/gorgon_nut/lotus/mustard_greens/okra/perilla/ramie/rhubarb/safflower/salsify/swiss_chard/water_chestnut/yacon；`[2] 12 个 age2`；`[3] 11 个 age0` |
| 🛑 **同物种跨龄同形** | 同一物种多个龄剪影完全相同（"没长大"） | `[5] cardoon_rosette_0..4 + _fruiting`（7 张） |
| ⚠️ **已知参考分配的结果** | 骨架是从同一 TFC 参考移植的 | `[39/41/46/53/60] buckwheat_N 与 einkorn_N`（docs/91 规律 3 记录：einkorn→buckwheat） |
| ⚪ **设计使然（需剔除）** | 方块贴图全满 256px ⇒ 必然同形 | `[4] 11 张 _head/_fruit/cantaloupe_side` |
| ⚪ **双段共用（需核查）** | 同一作物多龄共用 `_bottom`/`_top` | `[6] emmer_4..7_bottom`、`[15] quinoa_4..7_top` 等 |

> ⚠️ 关于 `⚪ 双段共用`：**TFC 原版也有**（`sugarcane`/`tomato` 的多龄 top 相同），
> 因此不能直接判废 —— 必须与 TFC 同族逐个对照后再定性。

### 2.4 与 `docs/87` 判据 5 的对照

- TFC age5 之间 IoU 中位 **0.342**；剪影**完全相同**（IoU = 1）在任何情况下都是违规。
- 本轮顺带核验了 fenugreek 修复后的撞形：**fenugreek_N vs adzuki_N 的 IoU = 0.19~0.35**（全部低于 0.342 基线）✅
- 修复前的实测：`adzuki_0` 与 TFC `lentil_0` **逐像素位置完全一致**；`adzuki_2` 与 `lentil_2` 同理
  ⇒ `adzuki` 全序列是 lentil 的"换色复制"，而 fenugreek 若也照 lentil 移植就会与 adzuki 逐像素同形（本轮 r12 即如此，r13 起改掉）。

## 六、第 41 轮·用户反馈修复（"前五龄与成熟龄不像一株 / 六龄茎干是纯色"）

### 8.5 补充：z-fighting 的根治（用户指出"这是 z-fighting 触发了，你根本没修复任何问题"）

**用户说得对** —— 我上一轮把 z-fighting 的噪点误读成了"两片正确穿插的细密纹理"，还宣布修好了。

**真实症状**（俯视 p70 最明显）：标定图的红绿区**布满红绿相间的细密斑点**；age4/age5 的叶丛上全是暗色噪点。

**我的 4 次尝试（前 3 次全部失败）**：

| # | 改法 | 结果 |
|---|---|---|
| 1 | z-buffer 用 `>=`（先画的赢） | ✗ 满屏噪点 |
| 2 | 改成 `>`（LEQUAL 语义，后画的赢） | ✗ 仍噪点 —— 因为**排序把"后画的"变成了"深度大（更远）的"**，反而让远的面赢 |
| 3 | 去掉画家算法排序（绘制顺序 = 模型面顺序） | ✗ 仍噪点 —— 共面的两面插值出的深度只有 **~1e-15** 的浮点差异，逐像素随机 |
| 4 | 给面名加 **0.02 深度偏置**（远大于浮点误差） | ✗ 仍噪点 —— 说明问题不在"两面之间"，而在**更多面之间的相互穿插** |
| **5** | ✅ **背面剔除**：每片板只画朝向观察者的那一面 | ✅ **2D 标定图与 age4 的 p70/p28 完全干净**，无任何噪点 |

**根因（最终结论）**：`block/crop` 的每片板声明了 `north` + `south`（或 `west` + `east`）**两个面**，
而零厚度板的正反两面**完全共面** ⇒ **结构性**的深度冲突，靠"调深度精度 / 调比较符号 / 加偏置"都治不了。
**唯一根治办法是剔除**（只画朝向观察者的面）——这也正是 MC 里 cutout 渲染的语义。

**修法**：光栅化时用屏幕空间叉积的符号做背面剔除（`if (det * backfaceSign < 0) continue;`），
`backfaceSign` 作为参数（默认 −1），并保留 z-buffer 处理"两片交叉"的深度关系。

**经验 40**：**零厚度共面的 z-fighting 只能靠"剔除"根治，不能靠"调深度"**。
判别方法：**看俯视角** —— 俯视时竖直面片几乎侧对视线，z-fighting 会被放大成满屏噪点，一眼可见。

**留证**：`px/ZF-FIX.png`（LEQUAL，仍噪点）· `px/ZF-FIX2.png`（去排序，仍噪点）· `px/ZF-FIX3.png`（加偏置，仍噪点）· `px/BF-TEST.png`（背面剔除后干净，但是逃避）· `px/PA-TEST.png`（**最终方案**：画家算法+面光照+镜像修正，干净且标定图方向正确）


### 8.6 最终修复方案（用户指出"你只是逃避问题，方块模型渲染并没有成功"之后）

**用户的批评是对的**："背面剔除"是**回避** —— MC 对无 cullface 的面一律渲染（`block/crop` 的正反两面都画），
剔掉它只是把共面问题藏起来，而且当时所有面同亮度，渲染出来根本不是 MC 的样子。

**最终方案（三处改动，都不是"剔除"）**：

| # | 改动 | 原因 |
|---|---|---|
| 1 | **u 方向修正**：`faceDefs` 的 `north/@(5,4,0,1)`、`south/@(7,6,2,3)` | 旧表把这两个面的 u 写反了 ⇒ 水平镜像 |
| 2 | **面光照**（MC 的 `Direction.getShade`）：`up 1.0 / north·south 0.8 / west·east 0.6 / down 0.5`，复用 tint 字段做颜色乘法 | 之前**所有面同亮度** ⇒ 两片交叉看不出来 ⇒ 加光照后立体交叉清楚可见 |
| 3 | **回到"面片级深度 + 画家算法"**（去掉逐像素 z-buffer 深度测试） | 见下 |

**为什么必须放弃逐像素 z-buffer（这是本轮最硬的技术结论）**：

> 零厚度板的正反两面**完全共面**。MC 靠 **GPU z-buffer**：两个共面三角形经过同一套顶点变换，
> 写入的深度值是 **bit-identical** 的 ⇒ `GL_LEQUAL` 下"后画的赢" ⇒ 结果**确定**。
> 而本渲染器在 **CPU 上按平面插值**深度（`z0 + (z1-z0)·s + (z3-z0)·tt`），两面走**不同的插值路径**
> ⇒ 结果差 **~1e-15** ⇒ 逐像素比较时**随机** ⇒ 俯视角满屏 z-fighting 噪点。

**我为此走的 5 次弯路（全部留证）**：

| 尝试 | 结果 |
|---|---|
| z-buffer `>=` | ✗ 噪点 |
| z-buffer `>`（LEQUAL 语义） | ✗ 噪点（排序把"后画的"变成"更远的"） |
| 去掉排序（顺序 = 模型面顺序） | ✗ 噪点（浮点差异仍在） |
| 面名 0.02 深度偏置 | ✗ 噪点 |
| 背面剔除 | ✅ 干净，但**不是 MC 行为**（用户判定为逃避） |
| **面片级深度 + 画家算法** | ✅ **干净 + 不剔除任何面 + 有面光照** —— 最终方案 |

**代价（诚实记录）**：两片交叉处不做逐像素穿插（MC 有 GPU z-buffer，会穿插）。
在 16×16 贴图 + 正常视角下差异很小；**但这也意味着：本渲染器只能当"初筛"，最终验收必须实机。**

**经验 41**：**CPU 端逐像素深度插值无法等价 GPU z-buffer 的共面一致性**。
判断渲染器深度处理是否有问题：**看俯视角**（竖直面片侧对视线时 z-fighting 会被放大成满屏噪点）。

### 8.7 最终方案（用户指出"十字交叉的纹理根本没被渲染出来"之后）

**用户说得对**：画家算法下**后画的那片整片覆盖了先画的** ⇒ 渲染结果看起来只有"一片"，十字交叉的立体结构被吃掉了。**逐像素深度竞争不能去掉。**

**最终四处改动（合起来才是"能渲染十字作物"的渲染器）**：

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | **u 方向修正**：`north/@(5,4,0,1)`、`south/@(7,6,2,3)` | 水平镜像 |
| 2 | **面光照**（MC `Direction.getShade`：up 1.0 / N·S 0.8 / W·E 0.6 / down 0.5，复用 tint 字段做颜色乘法） | 所有面同亮度 ⇒ 看不出立体交叉 |
| 3 | **保留逐像素深度竞争**（z-buffer） | 去掉它 ⇒ 一片整片覆盖另一片，**十字交叉结构消失** |
| 4 | **共面用 texIndex 做 tie-breaker**：`if (dz > 1e-9) continue; if (dz > -1e-9 && faceIdx >= zbufFace[zi]) continue;` | 共面/近共面时由**固定序号**决定，而不是由 ~1e-15 的浮点差异随机决定 ⇒ 消除 z-fighting |

**验证**（`px/CROSS-TEST.png` · `px/DONE-p28.png` · `px/DONE-p70.png`）：
- 标定图 p28：**左红右绿、白点左上**（方向对）+ **无噪点**；
- 标定图 p70：干净；
- age4/age5 的 p28/p70：干净、有面光照明暗层次、两片各自的可见部分都在；
- 六龄 2D 与 3D **方向一致**。

**本轮渲染器修复的全部弯路（6 次，全部留证）**：
z-buffer `>=` ✗ → `>` ✗ → 去排序 ✗ → 面级偏置 ✗ → 背面剔除（干净但是逃避）✗ → 纯画家算法（干净但丢掉交叉）✗ → **z-buffer + tie-breaker ✅**

**经验 42**：
- **"干净"和"正确"是两件事**：画家算法"干净"（无噪点）但**丢掉了交叉结构**；背面剔除"干净"但**剔掉了 MC 会画的面**。只有"**逐像素深度竞争 + 共面时用确定性规则决胜**"同时满足两者。
- 判断一份 3D 渲染是否真的渲染出了十字作物：**看它是不是"一片"** —— 若两片板的可见部分没有同时出现，就是画家算法在整片覆盖。
