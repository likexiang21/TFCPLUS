# 下一阶段新内容开发计划（2026-10-18）

## 一、当前基线

用户要求暂时跳过 c9 版本的实机回归，直接制定新内容开发计划。这个决定只改变施工顺序，不改变验收记录：干燥架八件批量、自动化余数、无 TFC Woodworking 的木工 JEI/完整流程仍标记为“待实机”，不能写成已通过。

当前可用基线如下：

- B 的独立木工、案板、石臼、刀架、木料堆和养蚕箱源码已完成静态门禁与离线构建。
- 养蚕箱界面问题已由用户实机确认解决。
- 草莓继续保留注册 ID，只禁止自然生成并隐藏三个显示入口。
- 可可继续沿用 `cupuacu` 大花可可树，产物使用 Firmalife 原版可可豆和原有发酵链。
- 所有存储物品的方块继续使用 TFC 容器接口。
- 新业务逻辑继续独立设计，不直接照抄示例模组、反编译实现或教程代码。

## 二、开发顺序总览

新内容按以下顺序推进：

1. **阶段 A0：A/B 全局内容台账与缺口审计**
2. **阶段 A1：A 作物与果树闭环补强**
3. **阶段 B1：已有 TFC/Firmalife 设备上的加工内容扩展**
4. **阶段 V1：植物、果树、物品和手册的视觉与说明收口**
5. **阶段 D1：温室、灌溉、地窖和自动化设备预研**
6. **阶段 C/D：大型系统和跨模组内容，暂缓到 A/B 的 P0、P1 缺陷清零后**

原计划的 A0 是下一次施工入口；现按用户新要求调整为厨具优先。A0 全局审计暂缓，必要的注册、配方和资源核对并入 docs/189 的 K0 厨具台账。

## 三、阶段 A0：全局内容台账与缺口审计

### 目标

把当前源码、JSON、标签、模型、贴图、JEI、Patchouli 和旧交接记录统一成一份当前事实清单，找出“注册了但不能玩”“能玩但没有说明”“输出没有用途”和“历史文档与当前实现不一致”的项目。

### 检查范围

- A 模组全部作物、果树、灌木、野生作物和果实。
- 草莓隐藏规则、可可 `cupuacu` 产豆规则和 Firmalife 兼容规则。
- B 模组全部物品、木工方块、设备方块、配方、标签和后处理链。
- 每个物品的注册、创造栏、JEI、Patchouli、模型、贴图、语言和掉落入口。
- 每个加工输入是否能到达产物，产物是否至少有一个明确用途。
- 配方是否引用真实命名空间，是否存在重复输出、孤儿资源和无效标签。

### A0 产出

- 当前注册 ID 与历史 ID 对照表。
- 物品到配方、配方到产物、产物到用途的可达性表。
- A/B 资源缺口表，区分代码问题、数据问题、资源问题和文档问题。
- “可以直接补数据”“必须改 Java”“必须实机确认”的分流清单。
- 一套 A0 静态门禁脚本；脚本只检查事实，不把实机结果伪装成静态通过。

### A0 禁止事项

- 不删除旧注册来修复显示或存档问题。
- 不在没有输入输出台账的情况下批量新增作物。
- 不复制示例模组的方块类、状态机或配方生成器。
- 不在本阶段改变用户已经确认正常的草莓、可可、封窑、调味、案板、干燥架和养蚕流程。

## 四、阶段 A1：作物与果树闭环补强

### 目标

优先补齐已经列入作物施工图、但存在断链或未完成收口的内容。每一批只处理一个完整垂直切片：种植 → 生长 → 成熟 → 采收 → 食品或材料属性 → 腐烂/保存 → 用途 → 手册说明。

### 施工分组

1. **单格作物和多年生作物**：先处理注册、气候、养分、成熟产物、种子返还、枯死状态和腐烂属性。
2. **水田作物**：核对水位、生长条件、收获物和 TFC 水田行为，不新增独立灌溉系统。
3. **攀爬、双格和莲座作物**：逐种检查方块状态数量、上下半块同步、支撑方块和破坏掉落。
4. **果树与结果枝**：先核对树种、叶片、枝干、生长和季节，再补产物与采摘冷却。
5. **野生作物与自然生成**：只为明确允许自然出现的物种接入生成；草莓灌木继续保持禁止自然生成。

### A1 完成条件

- 每种新增或修复的作物都有唯一 ID、种子/苗、产物、标签、模型、语言和手册入口。
- 气候、养分、成熟、枯死和腐烂行为使用 TFC 公开 API 与现有组件。
- 收获物不会变成无用途堆积物；至少接入现有食品、堆肥或 B 加工链之一。
- 旧存档能读取旧注册 ID；任何改名必须有迁移或兼容说明。
- 静态门禁、资源解析和离线构建通过后，才生成实机验证清单。

## 五、阶段 B1：已有设备上的加工内容扩展

### 设计原则

不为已有加工能力重复制造容器方块。新增内容优先使用 TFC/Firmalife 原版设备和配方类型，并沿用 TFC 容器接口、食品组件、腐烂判定和工具耐久规则。

### 优先顺序

1. **麦芽与谷物预处理**：连接 A 谷物到已有酿造或 Firmalife 原料，不改变原版酒液 ID。
2. **果酱、果干和果泥**：复用锅、桶、干燥架或 Firmalife 设备，明确新鲜度和容器返还。
3. **豆制品和面食**：使用石臼、案板、锅和 TFC 工作台，记录输入数量、输出数量和副产物。
4. **香料和汤料扩展**：继续使用现有调味入口，拒绝重复调味和腐坏食材加工。
5. **养蚕后处理扩展**：只在现有蚕茧、熟蚕、蚕丝线链稳定后增加用途，不改变已确认的养蚕生命周期。

### B1 完成条件

- 每个新增配方都有输入标签、输出用途、数量账和工具/容器返还规则。
- 食品输出继承合理的食品组件和新鲜度，腐坏输入被拒绝。
- JEI 与 Patchouli 能显示真实可执行的步骤。
- 不引入与 TFC/Firmalife 已有 ID 重复的基础物品。
- 所有涉及存储的方块继续遵守 TFC `InventoryBlockEntity` 或 `TickableInventoryBlockEntity` 契约。

## 六、阶段 V1：资源、JEI 与手册收口

- 逐批检查模型、贴图、方块状态、掉落、语言和 Patchouli 中英文文件。
- 不覆盖已经由用户确认的手绘资源；批量生成前先备份、预览和抽检。
- JEI 只显示当前可执行配方，隐藏兼容占位和不可达产物。
- Patchouli 说明实际操作顺序、温度、时间、容器和产物用途，不保留已废弃的历史数值。

## 七、阶段 D1：设备与自动化预研

只有 A1、B1 和 V1 没有 P0/P1 阻断后才开展：

- 温室：先复用 TFC 气候和作物 API，不新造温度体系。
- 灌溉：先定义水源、消耗、范围和存档数据，再决定是否需要方块实体。
- 地窖：优先复用 TFC 食品保存和温度接口，不复制独立腐烂系统。
- 自动化：先验证案板、石臼、干燥架、木料堆等已有容器的插入、取出、同步和破坏行为，再增加新的自动化设备。

## 八、统一验收与交接规则

每一批开发必须同时记录：

1. 参考了哪些公开 API、行为或数据格式；
2. 本项目独立设计的状态、输入输出和失败处理；
3. 修改的源码、资源、配方和门禁文件；
4. 静态检查、资源解析、构建和部署哈希；
5. 用户已实机通过、仅静态通过、待实机或明确跳过的项目；
6. 下一批的入口和回滚备份位置。

本计划不把暂时跳过的实机验证当作通过。用户恢复实机测试后，先验证 c9 待验清单，再根据结果决定是否关闭阶段二回归项。
