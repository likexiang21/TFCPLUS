## 一、Lead 自己复核结球模型 —— 抓到一个我上一轮**误判**的真问题

### 1.1 复核了什么
按用户「叶球模型存在问题，进行修复」，我用**真实几何**渲染了 5 物种 × 全龄：
`cabbage/broccoli/lettuce/napa_cabbage/cauliflower_age_0..5`，p28（玩家视角）+ p70（俯视）+ 大图 p28。

渲染器报告一律干净：`faces=22/22`、`missingTexFaces=0`、`inside-block OK`。
**几何层面没有退化面、没有越界** —— 上一轮那 4 个 bug 确实修掉了。

### 1.2 但是画面上是这样的（`px/LEAD-BALL-BIG28.png`，v4 = 上一轮交付状态）
- cabbage / broccoli age5：植株是一圈扇形绿叶，**正中只有一个扁平的暗绿方块**，
  像"叶丛中间挖了一个方坑，坑底有一块深色板"。
- 我上一轮的记录把这块暗方块解释成**「球顶面陷在坑底」**。
  🛑 **这是错的。** 把立方体单独标定后看清：`y=1..7` 的立方体被 **8/9/10/11 高的内层叶板四面围住**，
  叶板离立方体只有 **0.5 格**，而板顶比球顶**高 4 格** ⇒ 从 p28 看过去，
  视线完全被近侧叶板挡住（射线越过板顶后仍在 y≈10.7，远高于球顶 7）。
  **那个暗方块是叶筒内部的阴影**，球**一个面都没有露出来**。
- p70 俯视能佐证：俯视时球顶面可见，但四周是一圈**黑暗的空腔**（叶筒内壁之间）。

### 1.3 修法（v5）：把球抬成植株最高器官
原则：**球的顶面必须比内层叶板高 2 格**（2 是把"看得见多少侧面"从 0 提到约 2.3 格的最小代价）。

| 龄 | 立方体（改后） | 尺寸 | 内层板顶 | 球顶高出 |
|---|---|---|---|---|
| age2 | `[6,7,6] → [10,10,10]` | 4×3×4 | 8 | +2 |
| age3 | `[5.5,7,5.5] → [10.5,11,10.5]` | 5×4×5 | 9 | +2 |
| age4 | `[5,7,5] → [11,12,11]` | 6×5×6 | 10 | +2 |
| age5 | `[5,7,5] → [11,13,11]` | 6×6×6 | 11 | +2 |

- **叶板参数一个没动**（内层 x/z=4.5/11.5 高 8/9/10/11；外层 x/z=3/13 倾 22.5° 高 5/6/6/7）。
- 立方体 x/z 仍落在 5..11 内（age2 是 6..10、age3 是 5.5..10.5）⇒ **叶板仍在球外面，零相交不变**。
- 模型 bbox 由 `Y≤11` 变 `Y≤13`，`inside-block OK` 不变。
- 苗期 age0/1（无球）不动。

### 1.4 改后实看（`px/LEAD-BALL-V5-BIG28.png`、`px/LEAD-BALL-V5-AGES.png`、`px/LEAD-BALL-V5-TOP.png`）
- p28：**球顶面 + 上面两个侧面**清清楚楚地立在一圈叶子之上，读作"叶丛里顶出一个叶球"，
  不再是一个暗方块。age2→age5 是"同一株植物在长高、球在变大"，序列连续。
- p70：五个物种的球是画面正中**最显眼的整块**，顶面 + 四个上侧面都看得见。
- 遗留：内层叶板与外层斜板之间、以及球与叶板之间仍有**一圈暗缝**（两层叶板之间的空腔），
  俯视时比较明显。属"两层叶"的固有结构，本轮未处理。

### 1.5 教训
1. 🛑 **"模型在几何上合法" ≠ "玩家看得见"。** 上一轮我确认了"零相交、不越界、面无退化"就收工了，
   但**没有任何一次渲染证明球真的露出来了** —— 而它其实被挡得一个面都不剩。
   *判据要写成"画面上必须看到什么"，不能只写成"几何约束满足"。*
2. 🛑 **我把"叶筒内部的阴影"读成了"球的某个面"**，并据此判断"球在坑底但看得见"。
   误判的根源是**没有做单元素标定**（把立方体单独渲染一次，看它到底出现在画面哪里）。
   凡是"某个体块看起来是什么"的判断，先把它单独渲染一遍。

## 二、`check-geom.ps1` 报 `UVBad=6` —— 按设计，不是 bug

改完 v5 后 `check-geom` 对 `leafball_age_2..5` 报 **UVBad=6**（每个模型 6 个面）。
**已用改前备份复跑证实：改前同样报 6** ⇒ 不是 v5 引入的。

原因：立方体六面用**整张贴图** `uv [0,0,16,16]`，而 `check-geom` 的规则是
"UV 必须与板的世界尺寸 1:1"（`v=(16-h)..16` 底对齐）。二者天然冲突，
而"整张贴图"是**用户裁决**明确要求的（`AGENTS.md` 用户裁决①）。
⇒ **这 6 个 UVBad 属已知按设计项**，与 `sunflower_age_3/4/5_top` 同类，别再当 bug 追。

## 三、`Set-Content -Encoding UTF8` 会加 BOM（本轮真实踩到）

改这 4 个 json 时我先用了 `Set-Content -Encoding UTF8` ⇒ 文件头变成 `EF BB BF`，
而未改动的兄弟文件是 `123,34,99`（`{"c`）。
**MC 的模型解析对 BOM 不容错**（`GsonHelper` 严格模式），是潜在的"模型加载失败"。

✅ 正确姿势：
```powershell
$enc = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($p, $t, $enc)
# 复核首字节
[System.IO.File]::ReadAllBytes($p)[0..2]   # 应为 123,34,99
```
备份目录 `.probe/texture-design/bak-leafball-geom-v5-20260927/`（4 个改前原件）。

## 四、贴图实看发现（用户本轮的第二条指令：继续打磨瓜方块以外的贴图）

### 4.1 结球 30 张叶层贴图（子代理交付，**已复核验收**）
`{cabbage,lettuce,napa_cabbage,cauliflower,broccoli}_leafball_0..5.png`。
- ✅ **确认全部是活贴图**：每个物种有 `{sp}_age_N.json` 包一层，`parent` 指向共享的
  `leafball_age_N` 并把 `#0` 覆盖成 `{sp}_leafball_N`。**不是死资源**（这点必须先查，历史上踩过）。
- ✅ 贴图行与几何的对应**核对通过**：内层 0° 板读 `v8/7/6/5..16`，外层 22.5° 板读 `v11/10/10/9..16`，
  **底对齐 v16 = 地面**，画在底部的植株正确"站"在地面上。
- 实看：叶层是"中绿密叶、逐像素色阶跳动、锯齿状叶尖"的有机形态，比改造前明显好；
  age0/1 是小芽、age2 起铺开，序列连续。

### 4.2 napa 的"白色尖桩"（**已派单返工**）
`px/LEAD-NAPACLOSE.png` 左格（18×）：napa 的米白中脉被画成 **1px 宽、近纯白、直顶叶尖的竖条**，
一条条平行等距。渲染出来（`px/LEAD-A5-SIDE.png` 第 4 格）不是叶脉，是**一排白色尖桩戳出叶丛**；
同图右格 cabbage 的"中绿密叶"才是正确质感。
⇒ 返工要求：中脉 **2~3px 宽**、**两侧必须各留 ≥1px 叶肉绿**、**颜色用米白偏淡黄绿两档（不是纯白）**、
**最上 2~3 行留绿叶尖**、数量降到 3~4 条且长短错开。

### 4.3 结球 head 贴图（5 张）—— 构图本身就是错的（**已派单返工**）
`px/LEAD-HEAD-2D-BEFORE.png`（5 张并排 22×）实看，5 张都是同一个错误构图：
**"中间一大块苍白/灰白的圆角方块 + 外面一圈绿边"**。
- cabbage = 一整块近白米色板；lettuce = 近白黄块；napa = 几乎整张灰白空白；
  cauliflower = 一整块近白奶油色；broccoli = 深绿框 + 中间浅灰绿污渍 + **几个黑点**。
- 贴到立方体上 ⇒ **6 个面中心全是白的 = 玩家看到一个白盒子**（v5 渲染里 cabbage 就是一块白玉方块）。
- broccoli 更硬伤：实测 **74 个像素 LUM<45**，渲染成球顶的 **4 个黑点**，像被虫蛀。
- 🛑 教训：**"面内高光/渐晕"这种构图对立方体贴图是错的** —— 立方体每个面本来就是独立平面，
  整张 16×16 应当**边到边铺满"包叶表面"**，不要中心块、不要边框、不要渐晕。
- 返工时还追加了一条**几何变更通知**：球现在是植株最高器官、顶面是最亮最显眼的面，
  贴图必须比"淡黄绿到白"**暗一档**（cabbage 用中绿到黄绿，broccoli 用深蓝绿）。

### 8.2 新发现：`sisal` 与 `agave` 几乎无法区分
`px/LEAD-ROSETTE-A5.png`（莲座族 5 物种 age5，p28）实看：
kale（中绿 + 淡色叶）、**sisal（灰绿尖叶莲座）**、cardoon（中绿 + 灰绿尖刺）、
**agave（灰绿尖叶莲座 —— 与 sisal 几乎一样）**、purslane（亮绿 + 暗红斑点，辨识度最好）。
- sisal 与 agave **既共用几何、又几乎同色**，在画面上基本分不出。
- 现实依据：**agave（龙舌兰）叶有强烈的边缘锯齿 + 顶端硬刺，且常有淡黄/奶白色中央纵纹（斑叶）**；
  **sisal（剑麻）叶是光滑的蓝绿色剑形叶、只有顶端一刺、无斑纹**。
⇒ 修法方向：给 agave **加中央淡色纵纹 + 边缘锯齿**，把 sisal 压成**更冷更纯的蓝绿、无斑纹、只留顶端深色刺**。待派单。
- cardoon 与 kale 也偏近，但 cardoon 有灰绿尖刺、kale 有淡色卷叶，尚可分辨，暂不动。

## 九、本轮工具坑补充

1. **`Set-Content -Encoding UTF8` 会加 BOM**（见 §三）—— 写 json 一律用 `UTF8Encoding($false)`。
2. **`rr-review.ps1` 渲染普通双段作物必须在模型名上带 `_bottom` / `_top` 后缀**，
   且都会报 `OVERFLOW: Ymin=-1` —— 那是**原版 `minecraft:block/crop` 父模型**自身的 bbox（−1…15），
   **不是我们的模型坏了**，不要为此去改 json。
3. **双段"拼成整株"的 2D 做法**：把 `_top` 的 16 行放在**上**、`_bottom` 的 16 行放在**下**，
   合成 16×32 —— 因为游戏里下段方块在下方。**顺序反了会得出完全错误的结论。**
4. 🛑 **`System.Drawing` 的相对路径按 .NET 的当前目录解析，不是 PowerShell 的 `Set-Location`**
   （napa 子代理实测：一张拼图落到了**工作区根下的 `px\`**，而不是 `.probe\texture-design\px\`；
   根目录下已经躺着多个 agent 同类误落的文件）。
   ⇒ 用 `[System.Drawing.Bitmap]::Save()` / `FromFile()` 时**一律传绝对路径**（`Join-Path (Get-Location) ...` 或 `Resolve-Path`）。

5. **`if` 不能当表达式塞进 PowerShell 5.1 的 `-f` 参数**（`"...{0}" -f (if(...){...}else{...})` 会报

7. 🛑 **`Bitmap.FromFile()` 会锁住文件** ⇒ 对同一路径 `Save()` 直接抛
   **`A generic error occurred in GDI+`**，**而且此时内存里的位图是改好的、容易误判为"已保存"**（Lead 本轮实测踩到）。
   ✅ 正确姿势：
   ```powershell
   $img = New-Object System.Drawing.Bitmap((New-Object System.IO.MemoryStream(,[System.IO.File]::ReadAllBytes($p))))
   # ... SetPixel ...
   $ms = New-Object System.IO.MemoryStream
   $img.Save($ms,[System.Drawing.Imaging.ImageFormat]::Png); $img.Dispose()
   [System.IO.File]::WriteAllBytes($p,$ms.ToArray())
   # 必须重新从磁盘读回来复验，不要信内存里的值
   ```
8. 🛑 **对设计稿网格做"批量 `.Replace()`"极其危险**（与 §六-3 的"批量 Replace 误伤接缝行"同类）：

   ✅ **正确做法：不要手改网格，改为「用设计稿自己的调色板重新生成网格，再与旧网格逐行 diff」**：
   这样既修好了目标行，又**顺带证明了整张稿与 PNG 逐像素一致**（本轮 16 行里只有 y12 一行有差异，正是要改的那行）。
   ⚠️ 注意 PowerShell 的 `-eq` **不区分大小写**，逐行比对必须用 **`-ceq`**。
